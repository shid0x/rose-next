# CLAUDE.md — Rose Next Client

## Overview

Direct3D 9Ex (with plain D3D9 fallback) Win32 game client. Single-threaded game loop with packet-based server communication. All code is C++ built with VS2019 targeting x86.

## Key Subsystems

| Directory | Purpose |
|-----------|---------|
| `network/` | TCP socket management, packet send/recv (CNetwork singleton) |
| `interface/` | UI dialogs and HUD elements |
| `gameproc/` | Game state machine and processing |
| `gamedata/` | Runtime game data management |
| `ai_lib/` | Client-side AI behavior |
| `event/` | Event scripting |
| `sfx/` | Special effects |
| `sound/` | Audio playback |
| `terrain/` | Terrain rendering |
| `system/` | System-level (input, window) |
| `scripts/` | Lua scripting integration |
| `objectcommand/` | Character action/command processing |

## Important Classes

- **CObjCHAR** (`cobjchar.cpp/h`) — Base character object (player, NPC, monster). Manages server-authored damage presentation, HP reconciliation, pending death state, and animation states. Most combat display logic lives here.
- **CObjUSER** (`cobjuser.cpp/h`) — Player character (extends CObjCHAR)
- **CGame** (`system/cgame.cpp/h`) — Main game loop and state (`game.cpp/h` holds `CGAMEDATA`, i.e. `g_GameDATA`)
- **CNetwork** (`network/cnetwork.h`) — Singleton, manages Login/World/Game server connections
- **CGameOBJ** (`cgameobj.cpp/h`) — Base game object

## Networking

- Separate socket connections per server phase: Login → World → Game
- Packet handlers: `Recv_gsv_*()` for incoming, `Send_cli_*()` for outgoing
- FlatBuffers used for some packets (stat updates, movement)
- Packet receive: `network/recvpacket.cpp`
- Packet send: `network/sendpacket.cpp`

## Combat Presentation System

Critical architecture: live combat damage is server-authored only. Client presentation is allowed to decide *when* to show a hit, but never *how much* damage combat did.

- **Damage source:** FlatBuffer `DamageEvent` contains `event_id`, `defender_seq`, canonical `attacker_id`, `defender_id`, `raw_damage`, `damage_value`, `hp_after`, `presentation_kind`, and `lethal`, plus the display-only meter fields `skill_id` and `source_attacker_id` (presentation must never branch on them). `CombatSwing` wraps a `DamageEvent` plus motion data for confirmed normal attacks. Client-local `queued_at_ms` is stamped in `PushCombatDamageEvent()` only; it is not wire data and must not be serialized.
- **Queue ownership:** every `CObjCHAR` owns `m_CombatDamageQueue`. `StartConfirmedCombatSwing()` queues the event on the defender before starting the confirmed attack (`recv_combat_swing()` queues it itself only when the attacker is missing, as `MissingAttacker`, and presents it at once). Standalone `DamageEvent` packets are queued and either wait for a hit frame/projectile impact or present immediately depending on `presentation_kind`.
- **Area skill digits pop at action start (2026-10-18):** `Recv_gsv_DAMAGE_OF_SKILL` parks a skill hit on its caster only while the cast is live (`m_nActiveSkillIDX` / `m_nToDoSkillIDX`, cleared when the action motion starts) and otherwise presents it at once; the server sends it at action start (`Do_SKILL`). So a type-7/17 skill's digits show on its action's first frame, whatever its clip's events say -- moving the area event (24) changes only the visuals. Exceed Break splits Jrose's long cannon shot at its firing frame instead (see `src/sho_gameserver/CLAUDE.md` "Area Skills").
- **Presentation timing:** `Hitted()` pops one matching event for the current attacker (lagging hits from the same attacker may be folded into it, and in crowd mode it also paces the crowd drain -- see below). `NoEvent` means no HP change, no hit animation, no vibration, no hit sound and no digit -- except a bare MISS digit for a committed-dead attacker or a pending-dead avatar's swing (see Death / Phantom swings). Never resurrect timeout or missed-hit recovery behavior.
- **Crowd catch-up (2026-09-10 trial):** local-avatar fights with eight recent confirmed monster attackers use adaptive melee draining; membership lasts 3 s after the last confirmed attack and exits after 1 s continuously below eight. Membership is independent of the queue. At a real presentation, drain oldest nonlethal melee events toward 5% max HP outstanding, capped at six positive digits / sixteen events; misses advance silently. One-through-seven fights retain ordinary timing unless still exiting a prior crowd. Projectiles, lethal timing, healing-order guards and buff/impact feedback rules remain protected. See [doc/combat-crowd-drain.md](../../doc/combat-crowd-drain.md) for diagnostics, limits and the first in-game results: the player reported smoother presentation, and worst visible HP at lethal receipt fell from 31% to 9% across the two sessions. Further gameplay testing continues.
- **Projectile timing:** `ProjectileImpact` events stay queued until a bullet/skill projectile impact calls `Hitted()`. Generic immediate presentation must reject projectile events and push them back. **A projectile skill's splash rides its one shell:** a type-3 skill with `SKILL_SCOPE` hits one target, but the server spreads its status to every enemy around it (`Skill_ChangeIngSTATUS`), and those `GSV_EFFECT_OF_SKILL` payloads are queued as projectile-bound for targets no projectile ever reaches. `ProcEffectedSkill(true, skill, target)` therefore also releases status-only payloads (`!bDamageOfSkill`) of the same skill for other targets when that skill has a scope -- before 2026-10-17 they waited for the 10 s projectile timeout (Photon Cannon's Accuracy Down).
- **Hard-control interrupted swings:** `StartConfirmedCombatSwing()` records the exact server event id and defender for the attacker's current confirmed swing. Faint/sleep status application calls `CancelInterruptedCombatSwingPresentation()` before `SetCMD_STOP()`: if the swing's projectile has not spawned yet, the defender discards that exact event via `CombatPresentationQueue::discard_event()`/`DiscardQueuedCombatDamageEvent()` instead of leaving it to be consumed by the next attack. Nonlethal avatar damage lowers authoritative shadow HP and stages drift for the next real hit with no phantom digit; lethal avatar damage calls `MarkPendingAuthoritativeDeath()` and `PresentPendingAuthoritativeDeath()` immediately so the player is not alive-client / dead-server. Once `ActionBow`/`ActionGun` actually creates a projectile, `MarkPendingCombatSwingProjectileSpawned()` keeps the queued event for the real impact. (Pet weapon fire calls it on the cart; the swing is tracked on the rider, so it forwards to the rider like `ClearPendingCombatSwingPresentation` does -- before 2026-10-13 it did not, and a sleep/faint or a pre-empting cast mid-flight dropped the cart shot's digit.) `Hitted()` and explicit discard paths clear the pending swing state by event id.
- **Self-pre-empted swings are presented, not discarded (2026-09-14).** The discard above is for a *defender-caused* interrupt. When the interrupt is the **attacker's own next command** — a skill cast arriving while it still owes a hit frame — the server applied that swing at frame 0 and the honest rendering is to show it. `CObjAI::SetCMD_Skill2SELF/2OBJ/2POS` (client, after the `CanApplyCommand()` early-out, so a queued command that re-enters on `Execute` is covered) call `PresentPreemptedCombatSwing()`, which resolves the exact pending event and presents it through `PresentQueuedCombatDamageEvent()` → `ApplyPresentedCombatDamage()` (digit, HP, feedback, death). Same eligibility as the cancel path (a spawned projectile keeps its impact consumer) but deliberately **not** gated on `CS_BIT_ATTACK`: when the skill packet lands in the same frame as the `CombatSwing`, the attack motion never starts at all (`ProcCMD_ATTACK` never runs `Start_ATTACK`), and the hit is owed regardless. **Timing is decided by `m_bAttackSTART` on the motion object:** if no attack motion is attached, present at once; if one is running, the skill command only puts it in `CS_NEXT_STOP`, so its hit frame may still come — the first in-game test showed exactly that (hit frame at 0.42 s, fired right after the command into an empty queue, logged as `queued presentation miss`). So the hook then sets `m_bPreemptedSwingAwaitingMotionEnd` and leaves the event queued; either the hit frame presents it normally, or `Attack_END` (called from `Set_MOTION`'s prologue the instant a non-attack motion replaces it) presents it via the same function. Log signature for the deferred case: `pre-empted swing left to running attack motion` → `queued presentation pop` or `pre-empted swing presented ... reason attack motion replaced`. The local avatar and its mount are excluded (their skill flow starts at click time). Repro was Fearsome Terrasaurus King, whose when-damaged AI casts right after swinging: two 500-600 HP swings were discarded back to back and the killing blow presented death from a bar 1068 HP too high (`death correction deferred ... visible hp 1323 authoritative hp 255`). Log signature after the fix: `CombatTrace pre-empted swing presented` instead of `discarded without presentation ... reason swing motion cancelled`. The 3 s `Proc()` sweep is unchanged and still the tell for a motion lost some other way (MOVE/STOP repositioning, which the backlog self-corrects).
- **A remote caster's skill command is held behind the swing it would cut (2026-09-14).** Presenting the owed hit at pre-emption was honest but animation-less. The server itself sequences a cast after its own attack motion ends (its `SetCMD_Skill2OBJ` goes to `CS_NEXT_STOP`); only the packet is sent early. So `CObjAI::SetCMD_Skill2SELF/2OBJ/2POS` now push the command onto `m_CommandQueue` while `OwesConfirmedSwingHitFrame()` holds — pending swing set, projectile not spawned, defender still holding the event, and under `kOwedSwingHoldMs` (3 s, the orphan-sweep grace) — and `ProcQueuedCommand` will not pop it while that holds. The attack motion then starts/finishes normally, the hit frame presents the swing with its animation, and the cast pops right after. Bounds: the hold releases when the defender drops the event (its own sweep, death, despawn) or at 3 s, after which the present-on-pre-emption path applies; the attacker-side sweep waits on the queue being empty, so the time cap is what keeps the two from deadlocking. Skill commands only — move/stop are never held, so chase/repositioning are untouched, and each monster holds only its own cast. **The queue was written for the avatar's click-time flow, and three of its rules had to be re-stated for a remote caster** (each found in a boss session, 2026-09-14): (1) **valid at push** (`SetValid(true)`): `PopCommand` deletes an unvalidated skill command, and `GSV_SKILL_START` can arrive *after* the owed swing has popped the queue — a held Fireball was popped and deleted a second before its start packet, never played, and its damage was consumed by the next melee hit frame (`pop_for_attacker` is kind-agnostic and `Hitted()` cannot tell a melee frame from an impact -- bullets pass `bIsBulletHit`, but it only picks the hit effect, never which event is popped; pre-existing, left alone). (2) **Newest wins — never keep two skill commands queued.** `PushCommand` erases older result-less skill commands, and that is the wanted behaviour (the server's `SetCMD_Skill2OBJ` is single-valued, so a newer cast supersedes the previous one); marking them "result received" to keep both deadlocked the monster: a popped command re-queues itself while the queue is non-empty (`CanApplyCommand`), so a Charge and a Fireball superseded within the same second reshuffled forever and neither started. (That churn is gone since 2026-09-29 -- `m_bQueueGateBypass` stops a popped remote command re-queuing itself, see below -- but newest-wins remains the intended rule because the server's skill command is single-valued.) (3) **Start permission is counted per queued command.** `m_bCanStartSkill` is one flag per object and the *current* cast's action clears it (`ProcSkillAction` → `SetStartSkill(false)`), so a `SKILL_START` that arrived for the queued cast was eaten — the popped Fireball waited in `CS_STOP` for a start it had already received and the avatar died by the 6 s timeout. `Recv_gsv_SKILL_START` now counts it (`OnRemoteSkillStartWhileQueued`, reset when a new command is pushed) and `ProcQueuedCommand` grants the flag when it executes the queued skill command. A cast the server cancels before its `Casting_START` (a Faint on the caster) gets no start and waits until the next server command re-syncs the monster. Also, a legacy `GSV_DAMAGE_OF_SKILL` whose skill is still *queued* on a remote caster (`HasSkillCommand`) now defers to that cast's action frame like a running cast's does — it used to present immediately, a second before the animation. **`Recv_gsv_RESULT_OF_SKILL` needs the same rule** (2026-09-15): the server sends the result right after the damage payload, and that handler drains every parked payload whenever the caster has no active/pending skill — which a held cast is not, so the just-parked hit was presented at once anyway. Found on the Sikuku Jailer's 3590: in ten casts, the eight whose held command had already run before the packets parked correctly; the two where the packets beat the command (the attack motion still finishing after the owed hit frame, `CS_BIT_INT` keeping `ProcQueuedCommand` from running) landed a 400-digit a second before any motion. The tell in a log: `skill command held` → `GSV_DAMAGE_OF_SKILL` → `skill damage queued` two lines later → `SetCMD_Skill2OBJ[...]` *after* it; a parked cast shows the queue line a second or more after the payload. The avatar is excluded from all of it. Log: `skill command held for owed swing` → `queued presentation pop` → `SetCMD_Skill2OBJ[...]`; a hold with no `SetCMD_Skill2OBJ[...]` for that caster afterwards is either a server-side supersede/cancel (no damage packet ever comes) or a regression here.
- **Remote-cast watchdog (2026-09-14).** A monster's applied cast waits in `ProcCMD_Skill2OBJECT` for `GSV_SKILL_START` (`bCanStartSkill()`), silently, in `CS_STOP`. If that start never comes — the server cancelled or superseded the cast, or the start was consumed by something else — the monster sat in `CMD_SKILL2OBJ` for good and a lethal `ProjectileImpact` event it had queued on the avatar could only die by the 6 s hard cap (`presented (pending death timeout) ... attacker 0`, the "alive client-side, dead server-side, boss idle" moment). `m_dwRemoteCastWaitSince` (on `CObjAI`) now stamps the first wait (`remote cast waiting for skill start`) and after `kRemoteCastStartWaitMs` (3 s) abandons it: `remote cast abandoned, no skill start after N ms`, `Casting_END`, `CMD_STOP`, and `DiscardQueuedProjectileDamageFromAttacker()` releases that caster's projectile events on the target — a remote defender's lethal one presents, the avatar's lowers the shadow and leaves the death to the ordinary 1.5 s backstop (`has_live_lethal_pending` is false once the event is gone). Melee events are untouched (`discard_for_attacker_kind`). Also `Do_SKILL` returning 0 for a remote caster now sets `CMD_STOP` (`remote cast ended without action`) as the server does, instead of parking it. The avatar is excluded from both. **This is instrumentation as much as a fix**: the one occurrence so far (16:35:50, cast applied one second after the avatar's lethal fireball event was queued, no impact ever) could not be attributed from the log; the next occurrence will say which branch it sat in.
- **An abandoned cast still applies its status (2026-09-29).** Deader Rex's Astral Hex (3724) was held behind an owed swing, never got its `GSV_SKILL_START`, and the watchdog abandoned it -- while the server had already put ATK/DEF -30% on the avatar. The watchdog now calls `CObjCHAR::ResolveAbandonedCastPayloads(skill)`: every payload that cast parked on its caster is retired with no hit presented but its status half applied (`ResolveAbandonedPayload`: status only when the damage event was already queued and handled by the discard, else `ResolveEffectedSkillSilently`, which folds HP and presents only a lethal hit). `ProcTimeOutEffectedSkill`'s projectile-timeout branch used to drop a payload status and all; it goes through the same helper. Payloads are copied out of `m_EffectedSkillList` before any is resolved, since a lethal one reaches `Dead()` -> `ProcEffectedSkill()`, which erases from that list. **Why the start was lost is not known yet**; the trace lines added with it are: `GSV_SKILL_START` (branch taken: counted for queued command / armed / already armed), `queued skill start granted` or `queued skill command popped without a start` at the pop, `skill start consumed by action` (the timeline marker where a cast's action clears the flag), and on the status side `SkillStatusTrace effect parked on caster` / `client effect at receive` (`Recv_gsv_EFFECT_OF_SKILL`'s two paths -- the second applies at receipt and had no trace, so a status could land with no `client effect` line) and `abandoned cast payloads resolved`.
- **A cast that ends before its action frame presents its payload while it is still timely (2026-10-08, validated in game).** Crowned Asper King: the King's next `CombatSwing` replaced the release of a self-cast 3042 at frame 1 of 16 (hit event 25 at frame 5), and the 297 damage waited until `ProcTimeOutEffectedSkill` folded it silently 3.8 s later -- a bar drop with no number. A non-projectile payload is only parked while its cast is live (`Recv_gsv_DAMAGE_OF_SKILL`), so `!IsSkillCastStillLive()` means the cast has just ended: for a remote caster (`IsRemoteSkillCaster`: not the local player, not a mount/rider) a payload younger than `kEndedCastPresentMs` (1.5 s) is now presented in full (`ProcOneEffectedSkill`: digit, hit effect, sound, status) the moment its cast ends; older ones keep the silent fold at 3 s, so nothing ever lands late. Chosen for player comfort over a narrower "cut by the caster's own order" rule: it also covers monster skill motions with no action frame at all, whose damage used to drain the bar silently. One payload per sweep call (a lethal one reaches `Dead()`). Log: `ended cast payload presented`. **Why the release was replaced is not established** -- `CObjAI::SetCMD_ATTACK` should keep a running release as `CS_NEXT_STOP` -- so two traces name the path next time: `skill release replaced before its action frame` (in `Set_MOTION`: frame, new action, state, command, queue) and `skill release ended with its payload parked` (natural end, no drain).
- **The local avatar plays the swing it owes before casting (2026-09-29).** The avatar is excluded from everything above because its attack motion self-loops on the client's own clock (repeat 0) instead of one motion per `CombatSwing` -- and that clock runs a little behind the server's. A skill used mid-attack: the server finishes the swing it is in (applied at frame 0) and then casts; the client finishes *its* current motion and casts too, so it reaches the cast one swing short. Nothing ever animated that swing, and since the avatar's hit frames and bullets pop the target's queue oldest-first (`pop_for_attacker` is kind-agnostic), every later hit presented the event before it: **one skill cast = one swing of permanent lag**. Rot Tracker session (Scout): receive-to-present lag 1 s -> 6 s over the fight, two hits folded silently by the 8 s hard cap, skill digits landing on normal arrows, and the kill shown by the 6 s stale-lethal cap long after the monster died ("it stopped moving, then died"). Now `ProcCMD_Skill2SELF/POSITION/OBJECT` ask `CObjCHAR::PlayOwedSwingBeforeCast` first (via `HoldCastForOwedSwing`, only before the cast has begun): owed = the avatar's `MeleeHitFrame`/`ProjectileImpact` events on the defender of its last confirmed swing that had **arrived when the skill command applied** (`count_frame_presented_for_attacker` with an `arrival_seq` cutoff, `m_dwOwedSwingArrivedBy`; the cast's own damage event lands while the owed swings play, and counting it played one swing too many, took that event and pushed every later hit back a swing -- the cap hit three times in one fight, lag back to 4 s) minus its live non-dummy bullets at it (`CBulletMANAGER::CountLiveBullets`); if positive it plays one attack motion (repeat 1, `CS_ATTACK`) aimed at that defender, whose hit frame or arrow pops one event normally, then the cast proceeds. Bounds, per skill command (reset in `SetCMD_Skill2*`): only when the command replaced `CMD_ATTACK` (`Get_BECOMMAND`), at most 2 swings / 3 s, never out of range, on a dead defender, while the avatar is dying or mounted; past them the cast goes ahead as before. Two details that matter: the finished owed motion is **stood down** (`CS_STOP` + `Attack_END`, keyed on `m_bOwedSwingMotionPlaying`) exactly like `ProcCMD_ATTACK`'s refusal branch, because a motion left on its last frame with `CS_BIT_CHK` on re-fires every action point next tick (a second arrow); and while the owed swing plays, `CObjCHAR::SetCMD_ATTACK` **queues** an incoming attack (`IsPlayingOwedSwingBeforeCast`) -- after a quick skill the server may already be swinging again, and applying that attack would `Casting_END` the pending cast. Presentation only: the server's timing and the cast itself are untouched; on screen a skill used mid-attack starts up to one swing later. Log: `owed swing played before cast` -> `owed swings settled before cast`, or `owed swing not played before cast ... reason <why>`. Validated in game 2026-09-29 (Scout vs Rot Tracker): lag 0-2 s for the whole fight instead of drifting to 6 s, no avatar hit swept, the cap never reached; the player found the delayed cast unobtrusive. If players ever dislike it, the fallback on the table is presenting (folding) the owed hit at the cast instead of animating it. Known small side effect: after two owed swings the client can run a hair ahead of the server, so the next arrow can land before its `CombatSwing` (one `queued presentation miss`, a hit with no digit).
- **The local player's lagging hits are folded into the hit that lands (2026-09-29).** Even with the owed-swing play, a player casting every few seconds stays a cast cycle behind: the server swings through its casts while this client animates each owed swing and then the full cast, so the swings the server ran during one cast are owed at the next -- 1-3 s of standing lag, kills shown up to 4 s late (range and position were measured in sync: `avatar swing sync`, `avatar attack walks`). `CObjCHAR::FoldLaggingHits(..., 0, "own")`, called from `Hitted()` for `IsLocalAvatarAttacker()` once the hit being presented has waited `kOwnHitFoldAgeMs` (1.5 s), pops this attacker's other hit-frame/impact events on the target, any age -- oldest first (`pop_aged_frame_presented`), at most 4, and only the surplus over its bullets still in flight so no arrow lands blank -- and presents them *with* the current hit: one digit (the sum), combined flags, the newest checkpoint, death if any was lethal. One number rather than several by the player's choice (the crowd catch-up on hits taken shows several). The damage meter is untouched (it taps the push). Log: `own hits folded`. Validated 2026-09-29: 73 of 80 hits shown within 1-2 s (1-4 s before), the kill 1 s after the server's (4 s before), only two folds needed. **Trigger changed 2026-10-06:** it was the age of each *queued* hit, which caps the lag at roughly 1.5 s + one swing rather than removing it -- a Knight swinging once a second on Terrasaurus King sat 2-3 s behind for the whole fight (2-5 hits queued behind the one on screen, the next one at ~1.3 s), four folds in total. Now, as for hits taken, the trigger is the age of the hit being presented (`kOwnHitFoldAgeMs`) and everything queued behind it folds, any age. Expected cost: right after a catch-up the next hit frame can come before the server's next swing, one swing with no digit (`queued presentation miss`); if that shows up often, leave the youngest queued hit as a buffer. Validated the same night, Knight vs Terrasaurus King again: own hits shown within 1 s of the server 85% of the time (21% before), none at 3 s (12% before), four folds, no swing without a digit.
- **Hits taken from one attacker that fell behind are folded the same way (2026-10-06).** Server and client play a monster's attack clip at the same rate, so a swing lost to a cast or a chase is never caught up: each motion then pops the swing before its own (2-3 s standing lag on hits taken, bar ~2000 HP high, the killing blow arriving with the bar still healthy). The swing queued behind is always young, so the signal is the age of the hit being presented: on the local avatar, past `kIncomingHitLagMs` (1.5 s) and outside crowd mode, `FoldLaggingHits(..., 0, "incoming")` folds that attacker's other queued hit-frame/impact events into it (same bounds as own hits). Log: `incoming hits folded`. Validated: lag back to ~1 s.
- **A `CS_NEXT_STOP` left over after an attack motion must be stood down.** A `CombatSwing` arriving mid-motion applies `SetCMD_ATTACK` as `CS_NEXT_STOP` (frame checking on, no `CS_BIT_ATTACK`), so at motion end `ProcCMD_ATTACK` takes the `Goto_TARGET` branch; if that swing was already settled (folded), nothing reset the state and the held last frame re-fired every action point every other tick (bursts of `queued presentation miss` + attack sounds). That branch now sets `CS_STOP` + `Attack_END()` on the exact leftover state (`CS_NEXT_STOP2`, a skill action, must not match).
- **A swing may cut the previous swing's follow-through (2026-10-06).** A remote attacker's next `CombatSwing` used to wait for the whole previous attack motion (`CS_NEXT_STOP`), and at equal cadence that wait is never made up -- the root of the standing lag the fold above corrects. `StartConfirmedCombatSwing` now calls `CObjAI::StandDownSpentAttackMotion()`: when the running attack motion has no action frame left at or after `m_iCurMotionFRAME`, it is stood down (`CS_STOP` + `Attack_END()`) and the new swing starts next tick. Remote, unmounted attackers only. Log: `spent attack motion cut for next swing`.
  - **The cut must stay a fallback (2026-10-07).** It was firing on nearly every swing, and a cut a few frames short of the end *shows*: the restart blends from the current pose over the clip's 500 ms interpolation (`zz_bone::apply_channel_by_time`, weight `(t/500)^2` applied per frame), so the model holds the cut pose for ~150-200 ms and then lurches into the wind-up. The Dreadnaught King was cut at frame 57-58 of 61 (14-19 degrees from the loop pose) and visibly "snapped" into each attack; the normal Dreadnaught, at 59-60, did not. Why it was cut at all: the engine plays a clip at **integer** fps (`int(rate * fps)` in `zz_motion_controller::reset_speed`), so at 1.15 the clip ran at 34 fps against the server's 34.5 and lasted 25 ms longer than the swing cycle; and `Start_ATTACK` restarting the *same* clip left `m_iCurMotionFRAME` on the old frame, so the next `ProcMotionFrame` read "complete" and restarted it again a tick later (two `attack motion start` lines per swing). `Start_ATTACK` now plays remote swings `kRemoteSwingLead` (3%) faster, rounded up to a whole engine fps (`RemoteSwingPlayRate`; logged as `play`), and zeroes `m_iCurMotionFRAME` on the restart. The clip now ends 40-90 ms before the next swing and holds its last frame, as before the cut existed, without the lag building up.
  - **A tail of 150 ms or less is left to finish, never cut (2026-10-08).** The 3% lead does not cover the server's **10 Hz zone tick** (`_FRAME_PER_SECOND` in `gs_threadzone.cpp`): a swing is sent on the tick after it starts, so swings 1.82 s apart arrive 1.7/1.8/1.9 s apart, and an early one still cut Hebarn Officer Pazugenti at frame 58 of 61 (8 of 54 swings). Speeding clips up enough to absorb a whole tick would be 6-20%. Instead `StandDownSpentAttackMotion` returns false when the remaining frames take <= `kSpentTailWaitMs` at the clip's current playback rate, and the swing waits (`CS_NEXT_STOP`) as it did before 2026-10-06. That wait cannot accumulate any more because the clip is shorter than the cycle: one swing starts at most a tick late and the next makes it up. Log: `spent attack motion left to finish`.

- **A fresh checkpoint must also supersede, not just apply.** Being fresh is *not* on its own enough: `bStaleHealedCheckpoint` keys off `m_dwLastAuthoritativeSyncSeq`, so a checkpoint that does not advance that stamp leaves already-queued checkpoints looking valid, and the next one to reach its animation frame drags the bar back to its own pre-heal `hp_after`. `SetAuthoritativeHPFromDamageEvent` therefore advances `m_dwLastAuthoritativeSyncSeq` to `event.arrival_seq` (the event's own arrival order, not a fresh counter, so supersession stays exact regardless of when it is presented; never moves backwards) **whenever `bAllowRaise` is set — not only when the value actually rose.** Queued events do not touch the shadow until they present, so mid-deferral the shadow still holds *pre-hit* HP and a fresher checkpoint routinely reads as "lowering" against it while sitting well above the queued hit. - **Heal-in-flight checkpoint staleness:** `hp_after` is an *absolute* checkpoint valid only when the server computed it. A heal/potion/regen sync can arrive on the same TCP game socket while a hit is still deferred to its animation/impact frame, leaving the queued checkpoint outdated (lower than current truth). `DamageEvent.arrival_seq` (client-local, stamped at packet *receive* via `CObjCHAR::NextHPAuthoritySeq()` — at `PushEffectedSkillToList` for deferred skills so the source-packet order survives, in `PushCombatDamageEvent` for immediate paths) is compared in `ApplyPresentedCombatDamage` against `m_dwLastAuthoritativeSyncSeq` (stamped in `ReceiveAuthoritativeHP` -- every `Reconcile_HP` and heal checkpoint -- and by a `StatusTick` checkpoint). The guard never fires when no later sync exists (normal hits) or when the later sync is *lower* (more damage — handled by the existing checkpoint fold), so single-socket arrival order is the only ordering assumption. `arrival_seq` is not wire data; do not serialize it. The overshoot-clamp that raises the bar to the fresher HP is gated on `!has_pending_damage()`, so with another hit still queued (multi-hit skill, melee + skill) it is skipped and the bar would dip-then-snap; `ApplyPresentedCombatDamage` therefore *also* floors the visible bar at `min(visibleBefore, m_iAuthoritativeHP)` whenever the stale-healed guard fired, regardless of queue state (bounded by `visibleBefore` so a hit never visibly heals; lethal excluded). A residual ~0.1 s flash remains if the stale checkpoint presents a frame or two *before* the heal sync actually arrives — bounded, digit always correct, and a candidate for a future draw-layer eased/rolling HP bar (cosmetic only; must not touch authoritative HP/digits/death).
- **Digits vs HP:** `DamageEvent.damage_value` is the floating digit and feedback damage. Folded HP correction/checkpoint drift uses a local HP delta inside `ApplyPresentedCombatDamage()` and must not mutate `event.damage_value` or inflate `event.raw_damage`. Apply the displayed damage first, then clamp/fold only the remaining difference to the authoritative checkpoint; never add a pending correction blindly if the displayed hit already reached or passed `hp_after`.
- **Death:** death is explicit if `event.lethal`, `event.hp_after <= DEAD_HP`, or pending authoritative death is folded into an incoming hit. For the local avatar, `Reconcile_HP(DEAD_HP)` marks `m_bPendingAuthoritativeDeath` instead of showing synthetic huge damage. While pending-dead, avatar/cart outgoing hit frames present MISS/no damage unless the target event is also lethal; mutual death kills the avatar immediately after the monster's normal lethal presentation. **The fold stands down while the killing blow itself is still queued** (`has_lethal_pending()` on the avatar queue, checked in `ApplyPresentedCombatDamage` after the current event was popped): in a two-swing backlog the earlier, non-lethal swing presents as an ordinary hit and the lethal event presents the death at its own hit frame with its own digit. Before 2026-09-14 the earlier swing became the death (Terrasaurus King: 477 digit, death from a visible 843, the real 619 never shown). The stale-lethal fallback and the Proc() backstop still cover a lethal event whose consumer never fires. Log: `pending death left to queued lethal event`. An avatar/cart hit frame with **no event at all** while pending-dead also presents a bare MISS digit (`Hitted()` NoEvent branch, `ShouldSuppressOutgoingDamageForPendingDeath`): the server committed our death before sending it and every swing it ran was sent earlier on the same socket, so an event-less hit frame after that is a swing the server never ran — the same argument as the committed-dead-attacker phantom-swing rule, mirrored. Digit only, no `ClearStateByHitted()`. Added 2026-09-14 because the death now waits for the killer's impact and the player otherwise sees a couple of seconds of visibly connecting with nothing shown.
- **A lethal legacy skill payload arms pending death at receive (2026-09-14).** `GSV_DAMAGE_OF_SKILL` for a non-projectile skill parks its payload in the *caster's* `m_EffectedSkillList` until that caster's action frame (Terrasaurus King's Charge: 2 s), and pending death used to be armed only when the payload was converted into a queued event there. The server had already committed our death, so in the gap every avatar hit frame found no event and `Hitted()`'s NoEvent branch stayed silent — the "phantom hits" the pending-dead MISS digit exists to replace (`queued presentation miss … queue 0` twice before `skill damage queued`). `Recv_gsv_DAMAGE_OF_SKILL` now calls `MarkPendingLethalSkillPayload(caster)` when the deferred payload's `m_iHP_AFTER <= DEAD_HP` and the target is the avatar: pending death is flagged at once, and the caster + receive tick are remembered so `HasLiveLethalSkillPayloadPending()` (caster alive, under the 6 s cap) defers the backstop and stands the backlog fold down exactly like a queued lethal event does. `PushCombatDamageEvent` clears it when the payload becomes a queued lethal event from that caster; `ClearPendingAuthoritativeDeath` clears it with the flag. Log: `lethal skill payload pending`.
- **Pending-death backstop (never strand the avatar):** the pending-death mechanism normally relies on a *future incoming hit* to present the death. Two paths can leave the avatar flagged pending-dead with no incoming hit ever arriving: (1) the avatar kills its **only/last** attacker mid-swing (handled instantly — see drain-on-death below), and (2) a **no-attacker server kill** — DoT, fall damage, or an attacker that despawned/went out of range — that arrives via `Reconcile_HP(DEAD_HP)`. Without a safety net the player is alive-client / dead-server and frozen (server rejects input, nothing presents). `CObjCHAR::Proc()` therefore runs a backstop: if the avatar is `m_bPendingAuthoritativeDeath` and still alive client-side for longer than `kPendingAuthoritativeDeathTimeoutMs` (1500 ms), it forces `PresentPendingAuthoritativeDeath(NULL, "pending death timeout")`. `m_dwPendingAuthoritativeDeathTime` is stamped **only on the rising edge** in `MarkPendingAuthoritativeDeath` — the server can re-assert `hp=0` every frame, and re-stamping each call would push the timeout out forever so it never fires. `NULL` attacker is safe: the avatar's AI index is 0 (`AI_Dead` early-returns) and the lethal branch of `ApplyPresentedCombatFeedback` guards every `pAtkOBJ` deref. The timeout is intentionally short insurance, not the primary path — Layer-1 mutual-death-on-kill handles the common case with no delay, so the backstop should rarely fire. It is **not** a revival of timeout/missed-hit damage recovery: it only presents a death the server already committed.
  - **The timer defers behind a live lethal presentation (2026-09-14).** `PushCombatDamageEvent` arms the flag for *every* lethal deferred event on the avatar, and those have a real consumer coming — the killer's hit frame or the bullet impact. The flat 1.5 s timer raced them and won: against a ranged monster every shot landed **~2 s** after its `CombatSwing` was received (wind-up + flight; three consecutive non-lethal shots measured it), so the lethal one presented as `pending death timeout` with `attacker 0` **before the arrow was fired** — and the now-dead avatar made the client monster drop its attack (no-target branch of `ProcCMD_ATTACK` → `SetCMD_STOP`), so the shot never appeared at all. Log signature: `death correction deferred (lethal event queued)` → `presented (pending death timeout)` → `swing motion cancelled … state 0x0 command 0` for that event, with no `queued presentation pop` for it. Melee kills hit the same race whenever the hit frame is past 1.5 s (23% of swings measure ≥ 2 s). The backstop `if` therefore also requires `!m_CombatDamageQueue.has_live_lethal_pending(now, kStaleLethalSwingHardCapMs, DEAD_HP, fnPresentationStillLive)` — the same liveness predicate the orphaned-damage sweep uses, hoisted above the backstop, and the same 6 s hard cap as the spectator fallback. Timeline for a lethal event now: presented by the impact / hit frame (normal path); if the motion is replaced before the bullet spawns, the 3 s swing sweep → `DiscardQueuedCombatDamageEvent` presents the death itself; if the attacker vanishes the event leaves the queue and the timer fires at once; 6 s hard cap regardless. A pending death with **nothing queued** (DoT / fall via `Reconcile_HP`) is exactly the old 1.5 s. Cost: the window where the avatar's own outgoing hits show MISS grows from ≤ 1.5 s to "until impact". Nothing server-side interrupts the client monster meanwhile — after a kill the server's `ProcCMD_ATTACK` goes to `CMD_STOP` with **no** `Send_gsv_STOP`.
- **Spectator stale-death fallback:** remote/non-avatar defenders can also be left visually alive if this client receives a lethal `CombatSwing`/legacy melee death, queues it for the killer's hit frame, but the local representation of that killer never reaches the consumer frame (interrupted animation, command mismatch, already-past frame, missing attacker state). `PushCombatDamageEvent()` pre-marks non-avatar lethal defenders with `m_bDead = true`, and `CObjCHAR::Proc()` pops stale lethal `MeleeHitFrame` events after `kPendingAuthoritativeDeathTimeoutMs` (1500 ms) via `CombatPresentationQueue::pop_stale_lethal()`, then runs normal `ApplyPresentedCombatDamage()`/`Dead()` with the original final-hit digit. `MeleeHitFrame` deaths get the 1.5 s grace plus the live-swing deferral below; `ProjectileImpact` deaths wait for their bullet/skill impact and only ever pop at the 6 s hard cap (2026-09-23 — before that they were excluded outright, and a lethal projectile event whose bullet never presented and whose attacker left the client's sectors was stranded forever: `Del_Object` drains only events queued on the avatar, the orphan sweep excludes lethals, and the server never broadcasts a damage-killed mob's removal, so the monster stayed visually alive and unclickable for the rest of the session — one of the two mechanisms behind the "monsters dead server-side" tester report). **Live-swing deferral:** slow attack motions — cart / castle gear weapons, low attack speed — put the killer's hit frame legitimately later than the 1.5 s grace, and popping early killed one-shot targets mid-swing (stone-hammer battle cart was the repro). The `Proc()` call therefore passes a `swing_still_pending` predicate: while the event's attacker is alive, still in `CMD_ATTACK`, and still holds that exact `event_id` as its pending confirmed swing (for a cart/castle gear attacker the pending swing lives on the rider, `CObjCART::GetParent()` — the queued event is keyed to the cart index), the pop is deferred so the real hit frame presents the death. Deferral is bounded by `kStaleLethalSwingHardCapMs` (6000 ms) so a swing whose consumer never fires still resolves; as soon as the swing state stops matching (interrupt, new swing, attacker death/despawn), the original 1.5 s grace applies again immediately. The avatar's pending-death backstop (above) now shares this rule and this cap, through `CombatPresentationQueue::has_live_lethal_pending()` and the orphan sweep's `fnPresentationStillLive` predicate (which, unlike `fnSwingStillPending`, also treats any `ProjectileImpact` event as live while its attacker exists). If projectile creation/impact is explicitly discarded, `DiscardQueuedCombatDamageFromAttacker()` presents lethal remote defender deaths, but still silently discards nonlethal projectile damage and keeps avatar pending-death behavior unchanged.
- **Phantom swings (a dead attacker still swinging):** client attack motions are **self-repeating and self-looping**. `CObjAI::ProcCMD_ATTACK` calls `Start_ATTACK` again every time the previous motion ends, and `Set_MOTION` attaches with repeat count 0 so the engine loops the attack motion *forever* on its own (still true of the local avatar's motion; remote attackers have played one motion per confirmed swing since the fix below; `Dead()` calls `setRepeatCount(1)` explicitly for exactly that reason). Once a character is in `CMD_ATTACK` the client therefore animates swings at its own rate with no reference to server packets, while presentation is strictly server-event-driven. In the steady state this self-corrects — every `CombatSwing` runs `SetCMD_ATTACK` and `Set_MOTION`'s unconditional `controlAnimatable(0)`/`(1)` restarts the motion from frame 0, re-syncing to the server's swing. **Self-correction requires the server to keep sending swings, so every window where it goes quiet while the client stays in `CMD_ATTACK` is a phantom-swing window.** There are two. The first is **death**: the server applies the kill and stops swinging, but `Dead()` only runs when the killer's hit frame presents that lethal event — measured at ~1–2 s later, because the avatar's own presentation carries a standing ~1–1.5 event backlog. For that window the monster is dead server-side, alive client-side, and still swinging at nothing.
- **Those swings are presented as MISS, not silently.** `Hitted()`'s `NoEvent` branch is silent by design — an unbacked hit frame normally means the client does not yet know what happened, and inventing a result there is the false-MISS regression. A **committed-dead attacker is the one unambiguous case**: the server cannot run `Attack_START` on a corpse, and any swing it sent earlier is already delivered (same socket, lethal sent after it, TCP ordering), so once the client holds that attacker's death the swing certainly never happened. `CObjCHAR::IsPresentedDead()` gates it — it reads the presentation queue via `CombatPresentationQueue::has_lethal_pending()` as well as the `m_bDead` pre-mark, the queue being the primary source and the flag only a derived copy. This mirrors what the client already does for the local avatar's outgoing hits while pending-authoritative-dead. **Digit only, then return:** falling through would run `ClearStateByHitted()`, and a swing that never happened must not cancel the defender's buffs. No damage, no HP change, no hit effect, no sound, no vibration, nothing to the damage meter. `IsPresentedDead()` returns false for `g_pAVATAR` on purpose — `m_bDead` is only ever *set*, never cleared on revive, so reading it there would latch the player's attacks off permanently after their first death.
- **The second window is the target running away** (found and fixed 2026-08-30). When a target outruns its attacker, the server's `CObjAI::ProcCMD_ATTACK` leaves the attack state and re-closes via `Start_MOVE`, which **broadcasts nothing at all**. Nothing re-syncs the client for the whole chase, so it keeps looping its attack motion against its own dead-reckoned range check and produces hit frames with no server event behind them. `CombatTrace queued presentation miss ... queue 0` is the signature.
- **The fix is one animation per confirmed swing** (`CanStartConfirmedSwing()` in `CObjAI::ProcCMD_ATTACK`). Both `Start_ATTACK` call sites *in that function* are gated on the attacker holding a pending confirmed swing, **and** `Start_ATTACK` attaches a remote attacker's motion with `iRepeatCnt = 1` — gating alone is useless, because repeat count 0 is the engine's "loop forever" and the running motion keeps reaching action frames on its own. The refusal branch calls `Attack_END()` by hand, since `Set_MOTION`'s prologue normally fires it and this path deliberately does not call `Set_MOTION`. The local avatar and its mount are excluded (`IsLocalAvatarAttacker()`). **Note two further `Start_ATTACK` call sites are *not* covered** — `CObjCHAR::SetNewCommandAfterSkill_PET` drives `m_pObjCART->Start_ATTACK` on the `SA_ATTACK` / `SA_RESTORE` paths, so a remote mounted player can still start one unbacked swing after a skill.
- **Do not replace the motion in the refusal branch — tried and reverted.** Swapping in `GetANI_Stop()` there (to break the loop, and to get `Attack_END()` for free) makes the attacker visibly freeze and then **slide across the terrain** to catch up: the move branch drives position from the very next tick while the idle motion is still attached. This is the same trap as the older `GetANI_Stop()` parking attempt recorded below, and it reads worse than the phantom did. The repeat count is what stops the loop; nothing else needs to. **Two known gaps are accepted rather than fixed**, because every attempt to close them has regressed something visible: (1) an attacker that closes to range with no pending swing keeps `CS_BIT_MOV` and its run motion, animating on the spot until the next packet — brief in practice, since a server in range swings promptly; (2) `iRepeatCnt = 1` clamps at frame `n-1` and never wraps, and `ProcMotionFrame`'s in-order loop is `iL < iFrame`, so an action point on a motion's **final** frame would never fire. (2) is latent — 167 measured swings all presented, so no shipped attack motion appears to carry a last-frame action point — but check it first if a specific monster ever stops landing hits.
- **The monster's position drift is a *consequence* of that loop, not a separate bug.** An attack motion freezes movement (`CS_BIT_INT`), so every invented swing holds the client's copy still for a full motion while the server's copy keeps running after the player. Measured over one chase with temporary tracing (since removed): our copy of the attacker reached **1536** from where the server had it, while the server's own attacker position stayed 30-496 from our defender — i.e. the avatar was in sync the whole time and the monster was not. Verified after the fix: 75 swings, 75 presented, zero phantom hit frames, and that same drift down from a 1260 p90 to 114. **`PosGOTO` on a `CombatSwing` is the server attacker's own position** (`Goto_TARGET` sets `m_PosGOTO = m_PosCUR` before `Start_ATTACK`), which is what makes that decomposition measurable if it is ever needed again; `target_distance` is always 0 for the same reason.
- **Do not fix the drift directly — two attempts were reverted for it.** (1) Making `Adj_MoveSPEED`'s zero-distance case snap applies the whole accumulated drift as an instant jump onto the server's copy, which is adjacent to the player: the monster stops, vanishes and reappears on top of you. (2) Announcing a server-side break-off and presenting the unanimated swing removes the teleport but puts **damage digits on a monster that is visibly far away**, the presentation-detached-from-animation failure this subsystem exists to avoid. Leaving `CMD_ATTACK` also makes the `Proc()` orphan sweep's `Get_COMMAND() != CMD_ATTACK` test start passing, so anything that changes the command must also resolve pending swings.
- **Two approaches that were tried and rejected, both of which looked fine in the log:** (1) suppressing the `Start_ATTACK` re-arm in `ProcCMD_ATTACK` — useless on its own, because the motion already playing loops forever regardless; (2) parking the attacker in `GetANI_Stop()` — this does stop the swinging, but it freezes a monster mid-fight while its HP bar still shows 500–800 damage worth of queued hits, which makes the presentation backlog *visible* and reads worse than the phantom did. If you ever test a motion against `GetANI_Stop()`, compare `m_pCurMOTION` **by pointer**: `tagMOTION::m_nActionIdx` is stamped only by `CObjAVT::Get_MOTION`, so on a monster every motion reports action index `0` and a `Get_ActionIDX()` comparison silently never fires — one version of this fix shipped that way, logged a clean 127-frame window at "action 0", and changed nothing on screen. **Log evidence that a guard ran proves nothing here; the symptom is what the character is animating.**
- **Attacker dies mid-swing (drain-on-death):** the server applies a normal attack's HP at swing *start* (`Attack_START` → `Apply_DAMAGE`), while the client only presents it at the attacker's *hit frame*. If the player kills a monster before its swing reaches that frame, `Dead()` → `SetCMD_DIE()` interrupts the animation and the monster's already-applied `DamageEvent` orphans in the avatar's `m_CombatDamageQueue` forever. A lingering orphan keeps `has_pending_damage()` true, which gates off **both** reconciliation paths (`DeferCombatHPDriftIfIdle` and the checkpoint fold in `ApplyPresentedCombatDamage`), so the bars stay desynced (client HP > server HP) until the next unrelated hit/`UpdateStats`. `CObjCHAR::Dead()` therefore calls `g_pAVATAR->DrainQueuedCombatDamageFromAttacker(this)`: it discards every event the dying attacker queued on the avatar, lowers authoritative HP via `SetAuthoritativeHPFromDamageEvent` (which only ever lowers, so out-of-order drains are safe), and stages the lost HP as drift so the *next* presented hit silently folds it in (no phantom digit). A lethal orphan on the avatar is a **mutual death**: the attacker that just killed us is being interrupted into its own death motion this very frame and will never reach a hit frame, so no future incoming hit can fold our death in. The drain therefore both `MarkPendingAuthoritativeDeath` **and** `PresentPendingAuthoritativeDeath(pAtkOBJ, ...)` immediately — we already hold the authoritative lethal event and the killer object, so the avatar drops on the same frame as the kill (no freeze, no waiting on a server death packet). This is safe even though it runs inside the dying monster's `Dead()`: the avatar's own `Dead()` skips the drain re-entry via its `this != g_pAVATAR` guard. The `Proc()` backstop (above) still covers the case where this immediate present is somehow not reached. This is avatar-centric on purpose — each client reconciles its own bar; remote bars stay server-reconciled via `UpdateStats`. It is **not** a revival of timeout/missed-hit recovery: it only honors a *real* server event whose presentation animation was destroyed, mirroring the existing `DiscardQueuedCombatDamageFromAttacker` use for bullets that fail to spawn / projectile timeouts. `Dead()` is the single visual-death chokepoint (the `m_bDead = true` flags in `recvpacket.cpp` are pre-death markers; actual death is presented through `Dead()`), so one hook covers all kill paths.
- **Critical feedback is `PresentCriticalHitFeedback`** (camera shake when the avatar is hit, plus the attacker weapon's `EFFECT_HITTED_CRITICAL`). `Hitted()` calls it on `DMG_ACT_CRITICAL`; the three frame-less presenters (`PresentImmediateCombatDamage`, `PresentQueuedCombatDamageFromAttacker`, `PresentQueuedCombatDamageEvent`) call it through `PresentImmediateCriticalHitFeedback` on `DMG_BIT_CRITICAL` in `raw_damage`. Before 2026-10-16 they drew only the digit, so skill crits (katar Hawker/Raider, server `Is_KatarSkillCRITICAL`) and pre-empted crit swings showed no crit. On a monster the effect is anchored at the damage digit (`GetOverheadZ()`) and draws just above it at any size: at the feet (it draws at chest height) it was hidden inside big monsters (Giant Fiery Snapper) and covered the digit on mid-sized ones (Baby Desert Asper), whose head is about the effect's height. Avatars keep the feet anchor (chest, below their digit) unless taller than 250 cm.
- **No client damage math:** live client combat must not call `CCal::Get_DAMAGE()` or `CCal::Get_SkillDAMAGE()`. Those APIs are server-only for live combat; client usage belongs only in explicit offline/test paths.
- **A stranded orphan disables reconciliation permanently — the sweep is what makes the system self-healing.** Drain-on-death only covers the attacker that *dies*. Every other cancellation path (`Hitted()`, `CancelInterruptedCombatSwingPresentation()`, `DiscardQueuedCombatDamageEvent()`) also needs the attacker object to still exist and to still be tracking that exact `event_id`, and three ordinary situations break both assumptions: the attacker walks out of your sectors (`gsv_SUB_OBJECT` → `CObjectMANAGER::Del_Object`), the zone changes (`CObjectMANAGER::Clear`), or it had **two swings in flight** and only the newest was ever recorded in `m_dwPendingCombatSwingEventId` (`StartConfirmedCombatSwing` overwrites the id without discarding the previous one; the `Proc()` swing sweep then cancels only the tracked one). Because `has_pending_damage()` gates **both** reconciliation paths, one such entry stops HP convergence for that character *for the rest of its life* — every later hit moves the bar by its own digit alone and the drift only accumulates. This is why the drain-on-death unit tests can all pass while the feature looks broken in a real session: the mechanism is correct, it just never runs again after the first poisoning. Three things close it: (1) `Del_Object` drains the departing character's events off the avatar first — also **before** the client object slot can be recycled, since `attacker_id` is a client index and a reused slot would otherwise hand the stale event to whatever spawns next; (2) `Clear()` drops the avatar's queue wholesale on zone change (the server re-states HP at `JOIN_ZONE`, so a checkpoint from the zone you are leaving has no authority in the one you are entering); (3) `CObjCHAR::Proc()` runs a timed **orphaned-damage sweep** (`CombatPresentationQueue::pop_stale_orphan`) as the generic safety net for anything else. The sweep resolves silently — `SetAuthoritativeHPFromDamageEvent` + `DeferCombatHPDriftIfIdle`, **no digit, no hit effect** — because the damage was never presented and inventing it late is a phantom hit. Grace is `kOrphanedDamageGraceMs` (3000 ms, comfortably past any hit frame incl. castle gear's 0.70–1.17 s) with a `kOrphanedDamageHardCapMs` (8000 ms) hard cap so an attacker that swings forever at *someone else* cannot pin an event in your queue. **Lethal events are excluded on purpose** — `pop_stale_lethal` and the pending-death backstop present a *death* for those, and folding one silently would strand the player alive-client / dead-server. Projectile events are held to the hard cap while their attacker exists, whatever its state: a bullet's timing belongs to the bullet, and a skill projectile arrives as a FlatBuffer `DamageEvent` that never records a pending swing to check against.
  - **The commonest stranding source turned out to be your own death.** Validated log: the avatar dies, its summons despawn mid-swing, and every event those summons had queued on their targets is orphaned at once — nothing drains them, because the drain hook is on the *attacker's* `Dead()` and a despawned summon never presents one. Before the sweep those monsters' bars never reconciled again for the rest of their lives. The sweep catches them at the 3 s grace (`orphaned damage swept … age 3001`). Any death with pets out hits this, which is why the drift reproduced so easily.
  - **Client-synthesized event ids must come from `Rose::Combat::kClientSyntheticEventIdBase`** (`0x80000000`). The five legacy `GSV_DAMAGE` / `GSV_DAMAGE_OF_SKILL` paths (four `GSV_DAMAGE` branches plus `ConvertDamageOfSkillToDamage`) mint their own ids because those packets carry none, and they share one per-defender queue with the server's `g_nextCombatEventId`, which starts at 1. `event_id` is the key for `push()` dedupe, `discard_event()`, `has_event()` and `ClearPendingCombatSwingPresentation()`, so an overlapping id **silently drops** a hit on push (no digit, HP checkpoint lost) or discards the wrong event out from under a live swing. Two of the four counters still started at 1 — observed live with server ids at 1..330 and legacy skill ids at 1..10 in the same five minutes. The old 1e6 offsets only deferred it: a busy zone's event rate walks the server into those bands within days of uptime. Setting the high bit is what actually separates the spaces.

- Key methods: `PushCombatDamageEvent()`, `Hitted()`, `ApplyPresentedCombatDamage()`, `PresentImmediateCombatDamage()`, `Reconcile_HP()`, `MarkPendingAuthoritativeDeath()`, `PresentPendingAuthoritativeDeath()`, `CancelInterruptedCombatSwingPresentation()`, `DiscardQueuedCombatDamageEvent()`, `DrainQueuedCombatDamageFromAttacker()`, `DiscardQueuedCombatDamageFromAttacker()`, `CombatPresentationQueue::pop_stale_orphan()`

### AI Chase Movement (CMD_MOVE with target)

`Recv_gsv_ATTACK` routes monster attacks through `CObjCHAR::SetCombatAttackIntent` → `SetCMD_MOVE(target=avatar)`, **not** `SetCMD_ATTACK`. The monster walks toward the player in `CMD_MOVE` state and the actual swing is started later by `CombatSwing` / `StartConfirmedCombatSwing`. This means `CObjAI::ProcCMD_MOVE` runs for chasing monsters, not just for click-to-walk player input.

`CObjAI::ProcCMD_MOVE` has two distinct paths and the dispatch matters for combat sync:

- **USER mover** (`this->IsUSER()`): use `Goto_TARGET(pTarget, AVT_CLICK_EVENT_RANGE | NPC_CLICK_EVENT_RANGE)` — these click-event ranges (1000 / 250 in `datatype.h`) are UX values for "I clicked on someone to talk to them", not combat ranges. They are correct **only** for player-initiated walks. **Exception (2026-09-22): a player walking to a player where both are `is_pvp_enabled()` chases to `Get_AttackRange()` instead.** A PVP attack click comes back as `GSV_ATTACK` → `SetCombatAttackIntent` → `CMD_MOVE` with an avatar target, which landed in this branch and `SetCMD_STOP()`'d the attacker at the 10 m interact ring; it then stood still for the 1-2 s the server needed to close the distance, until the first `CombatSwing` restarted it (alpha test #2: "I click a player, stop on the way for no reason, then resume"). Monsters never showed that, because an `OBJ_MOB` target matched neither USER sub-branch and fell through to `Goto_POSITION()` -- with the monster's **centre** as `m_PosGOTO` and a stop distance of 0, which was its own bug (2026-10-23): the walk stopped only when the server's first `CombatSwing` switched the avatar to `CMD_ATTACK`, so a swing more than ~0.2 s late (melee range / run speed) left the player standing at the monster's centre, and `ProcCMD_ATTACK` never steps back out. **The `OBJ_MOB` sub-branch now halts at `Get_AttackRange()` and waits for the swing. It stops early only and never chases** (still `Goto_POSITION` toward the clicked point): a walk to a spot interrupted by a cast on a monster also arrives here with a monster target, and there the server stops (see `CommandToRestoreAfterSkill`, below). Check with `avatar swing sync`: `client_dist` should sit near `range`, not near 0.
- **Non-USER mover (monster, NPC, summon)** with a `pTarget`: use `Goto_TARGET(pTarget, this->Get_AttackRange())` so the chase re-reads `pTarget->m_PosCUR` each tick via `Restart_MOVE` and follows the live player position, halting at the monster's own attack range where the server starts its swing.
- **No target** (server-side move to a position): fall through to `Goto_POSITION()`.

**A skill cast during a player's attack walk must restore an attack, not the walk (2026-10-15).** The server holds that walk as `CMD_ATTACK`; this client holds it as `CMD_MOVE` on the monster. A restoring (`SA_RESTORE`) skill cast mid-walk made the server go back to `CMD_ATTACK` and close the distance silently, while this client put back a move whose goal the cast had reset to where the player stood, and stopped. The player then fought 10-15 m from where the server had them (`avatar swing sync: self_drift 994` for a whole fight), each side's monster chasing its own copy of the player, and the monster "teleported" once the fight broke off. `CObjAI::CommandToRestoreAfterSkill` now saves `CMD_ATTACK` for a player in `CMD_MOVE` on an `OBJ_MOB`. A walk to a spot has no target and a walk to an NPC has an NPC target, so a player in `CMD_MOVE` on a monster is always an attack walk. Do not make that branch chase in `ProcCMD_MOVE` instead: a walk to a spot interrupted by a cast on a monster also comes back as `CMD_MOVE` on the monster (the cast set the target), and there the server stops.

Do not collapse these paths. The historical bug: every mover used `AVT_CLICK_EVENT_RANGE` (1000) and called `SetCMD_STOP()` when crossing that ring, freezing brawlers ~10 m from the player while the server kept advancing them and landing real hits — visible as "monster suddenly stops, then resumes" with client HP > server HP. Sister bug if the non-USER path is changed to `Goto_POSITION()`: the chase walks to a stale snapshot of the player position at packet-arrival time and only re-aims when the next `gsv_ATTACK`/`gsv_MOVE` arrives, producing the kiting-to-first-position visual artefact.

### Attack Speed Presentation

The server owns the swing cadence: its `CObjAI::Start_ATTACK` plays the attack motion at `total_attack_speed() / 100` and applies damage at frame 0 of each loop. The client only *animates* that cadence, at `Get_fAttackSPEED()` read once per `Start_ATTACK`, and nothing on the wire carries a per-swing rate — so whatever this client holds in the attacker's `stats.attack_speed` is what the observer sees. Three independent defects each put a remote player at **exactly 1.00x**, which is why the first multi-player test (2026-09-19) came back as "player A sees B attack at normal speed while B is visibly fast":

- **An avatar's `stats.attack_speed` is the server total, applied verbatim.** `gsv_AVT_CHAR.m_nPsvAtkSpeed`, `gsv_SPEED_CHANGED.m_nPsvAtkSPEED` and `UpdateStats.attack_speed` are all filled from `total_attack_speed()` — weapon + passives + running buffs + goddess + server.toml `base_attack_speed` (35) — and the 2005 "passive only" field names lie. `CObjCHAR::Get_fAttackSPEED` (reached by `CObjAVT`/`CObjUSER` only; mobs, NPCs and carts override) therefore returns `stats.attack_speed / 100`, floored at 0.3, and nothing else. It used to add `m_EndurancePack`'s INC/DEC_ATK_SPD and the goddess term on top, which counted every attack-speed buff twice: a buffed player saw their *own* swings faster than the server ran them, with the surplus hit frames logging `queued presentation miss`. Same rule as `stats.move_speed`, which the client never re-buffs either. `CObjMOB::Get_fAttackSPEED` keeps STB + endurance delta because the server never syncs a monster's speed.
- **Never overwrite a synced speed at creation.** `Recv_gsv_AVT_CHAR` writes the packet value *before* `Add_AvtCHAR` → `CObjAVT::Create`, which used to clobber it with `1500 / (WEAPON_ATTACK_SPEED(BODY_PART_WEAPON_R) + 5)` — a slot index (8) fed to an item-number macro, i.e. `LIST_WEAPON` row 8 "Elven Sword", speed 10 → 100 → 1.0x for every player until a `GSV_SPEED_CHANGED` happened to arrive for them (level-up, equip change, buff). This was the primary cause of the report. `Create` now seeds only while the value is still 0 (the local avatar, created before its first `UpdateStats`), from the weapon actually equipped.
- **`Set_MOTION` re-arms rate and repeat count on every attack-motion call.** `Chg_CurMOTION` returns false when the motion pointer is unchanged, and between a remote attacker's swings the refusal branch of `ProcCMD_ATTACK` calls `Attack_END()`, which resets the animatable to 1.0 *without* replacing the motion (deliberately — see the phantom-swing notes above). A second swing on the same clip therefore replayed at 1.0x whatever `Get_fAttackSPEED()` said: a third of an avatar's swings (`GetANI_Attack` picks one of three clips at random) and every standing second-and-later swing of a monster (one clip). The `else if (bAttackMotion)` branch in `Set_MOTION` fixes it, scoped to attack motions so move/stop playback is untouched. The server's `Set_MOTION` now stores `m_fCurAniSPEED` on every swing too, so an attack-speed buff applied mid-fight changes the cadence on both sides at the *next swing* (it used to wait for the next motion change).

Diagnostics: `CombatTrace attack motion start: obj N rate R synced S repeat K` (Debug) fires once per swing start. Pair it with `combat swing received` for the same attacker: with the rate right, receives and `queued presentation pop` are 1:1. An attacker animated slower than the server swings shows more receives than pops plus `orphaned damage swept` folds for its events — on screen, a 1.0x animation with fewer digits and an HP bar dropping in silent chunks. The dev target window's "Attack speed" line shows `Get_fAttackSPEED()` of the targeted object. Left alone on purpose: the `IsA(OBJ_AVATAR)` branch of the buff-magnitude estimate in `Recv_gsv_EFFECT_OF_SKILL` (it has no `AT_ATK_SPD` case, so a remote avatar's endurance value is a flat-only guess — display-only now), and the dead `GetPsv_ATKSPEED` / `m_nPsvAtkSPEED` scaffolding from the abandoned client-side formula.

### Cart / Castle Gear Combat

When `GetPetMode() >= 0`, combat state is split between the rider avatar and the `CObjCART`:

- `CObjCHAR::SetCMD_ATTACK` must route mounted attacks to `m_pObjCART->SetCMD_ATTACK` before the rider-side `CanApplyCommand()` gate. If the rider queues the first post-mount attack on itself, the server can already be processing `CLI_ATTACK` while the client still looks idle.
- Server still attributes some legacy damage packets to the rider (user index). `Recv_gsv_DAMAGE` re-keys the damage event to the cart's client index when `pAtkOBJ->GetPetMode() >= 0 && pAtkOBJ->IsUSER()`. Damage must only be queued once under that canonical cart/castle-gear attacker index.
- Legacy damage timeout and missed-hit recovery are retired for live combat. If a hit frame has no matching server event, no presentation occurs.
- `ActionInFighting` case 21 and the rider-side `ActionBow` / `ActionGun` attack frames must skip `Hitted()` / projectile spawning when `GetPetMode() >= 0 && !IsPET()`. The rider's attack motion is visual only; the cart/castle gear is the source of truth for hit timing.
- The first mounted attack after `Drive Cart` can fail if the player attacks before moving even once. Root cause: cart runtime movement state was only being fully primed by mounted move flow. `CreateCart` and `SetCMD_PET_ATTACK` now copy the rider's move speed / move mode into the cart up front so the first attack can immediately path toward the target.
- `CObjCART::Get_fAttackSPEED()` falls back to the rider's `stats.attack_speed` (then a hard 100 default) because the cart's own `stats.attack_speed` is never synced from the server. A 0 attack speed produces motion speed 0 → NaN bone transforms → `zz_octree` min <= max assertion crash.
- **A stop on the rider does not reach the mount by itself.** `CObjAI::SetCMD_STOP`'s forward to the pet (`SetCMD_PET_STOP`) sits inside `#if defined(_GBC)`, which no build defines, so code that stops a rider must stop the cart too (`Stop_Cart()`). Sleep/faint (`CEnduranceSkill`, `interface/cenduranceproperty.cpp`) do since 2026-10-13: before, a stunned castle-gear rider kept the gear's attack order and the self-looping avatar attack motion swung at nothing (`queued presentation miss ... queue 0` every swing) until the next order.

### Cart / Castle Gear Visual Loading

Cart visual creation (`CreateCart` / `CreateCartFromMyData` → `CObjCART::Create`) has several silent early-returns. Key gotchas:

- The union at `cobjchar.h` around line 1348 has **inverted** field names vs `RIDE_PART_*` indices: `m_sEngineIDX` is actually slot 0 (BODY) and `m_sBodyIDX` is slot 1 (ENGINE). Rest of the client follows the same inversion, so data round-trips — but it reads wrong.
- When `list_pat_skeleton.stb` has no skeleton entry for a cart body, `io_basic.cpp` synthesizes one from the body-item part data. Without this fallback, cart creation returns false while the server-side drive-mode speed is already applied (`recvpacket.cpp` unconditionally writes `move_speed` from the `TOGGLE_TYPE_DRIVE` packet before `RideCartToggle(true)` runs) — the player ends up moving at cart speed with no cart model.

### Terrain Streaming Performance

Chunk-display hitches are **resource creation at first render**, not chunk file I/O. `terrain/CLAUDE.md` has the full picture; the two things to know before touching it:

- **Measure lead time, not queue depth.** Frames between a resource being queued and being force-loaded is what tells you which fix applies. Terrain meshes measured **1 frame** (no amortiser can help — cap the inserts, `[VIDEO] TERRAIN_INSERTS_PER_FRAME`); textures measured **200-300 frames** (the amortiser had slack and wasted it — `[VIDEO] LOAD_BUDGET_US`). Applying either fix to the other problem does nothing.
- **A map tile that is allocated but not `MAP_USING` next to the player crashed the client** (2026-09-18, walking towards the Skaaj lighthouse; `GetViewFrustumEq` on `this = 0x22C0`, i.e. NULL plus the member offset). `ClearAllQuadPatchManager()` nulled the nine neighbour pointers but not `m_isUse`, and `UpdatePatchManager()` only rewrote the flag for a NULL or in-use neighbour, so a freed, dirty or still-loading slot kept last frame's TRUE beside a NULL pointer, and the next cull wrote through it. Both sites now clear the flag. The one unexplained Karkia crash of 2026-09-09 was preceded by the same `DeferredFreeMAP` teardown and is very likely this bug.
- Diagnostics are opt-in: `[VIDEO] STREAM_SPIKE_LOG_MS` (0 = off) plus the `MapIO:`/`Flush:` debug-HUD rows and `/perfreset`.
- **`STREAM_SPIKE_LOG_MS` only fires on streaming time**, so a hitch from any other phase writes nothing and is indistinguishable from a smooth frame. `[VIDEO] FRAME_SPIKE_LOG_MS` (0 = off) triggers on *total* frame time and logs that frame's own phase split (`netin/logic/scnupd/shadow/render/ui/present/oth` + the logic sub-slots + the flush counters), which is what names a non-streaming hitch. Reach for it first; the streaming log narrows down what it finds. Run with `VSYNC=0` while hunting, or the vsync wait in `present` masks everything.

## Skill Statuses End On The Server's Word, With A Backstop (2026-10-13, deployed; the backstop has not fired in game yet)

A skill status (`CEnduranceSkill`) has no timer of its own: it leaves when `GSV_CLEAR_STATUS`
arrives (`DeleteEnduranceState`). A status presented *after* that packet -- a payload parked on its
caster and applied at a late action frame, or by the abandoned/ended-cast resolution -- therefore
stayed on screen (burn icon and effect, no ticks) until the next status change on that character
(alpha report: "burning but no damage after the duration"). Two changes:

- `ApplyEffectOfSkill` backdates the new entity to the payload's arrival (`m_dwCreateTime`), since
  the server's countdown started when it sent the packet.
- `CEnduranceSkill::Proc` ends a status older than its `SKILL_DURATION` + 5 s
  (`kServerClearGraceMs`; the server clears at most ~2 s past the duration). Log at Info:
  `Status expired without a server clear`. Only state types the server counts down
  (`IsServerTimedState`: poison, max HP/MP, the held states 6-28, taunt) and only entities with a
  skill index -- the ones built from spawn flags carry a placeholder duration of 100 and stay
  server-driven, as do regen, the summon marker and revive.

**Weapon swaps and spawn-flag statuses (2026-10-28, solo swap + unknown timer validated).** The client mirrors
the server's weapon-swap clear (`Recv_gsv_EQUIP_ITEM` -> `ClearR/LWeaponSkillEffect`), and the
server only clears a status whose `LIST_STATUS` gain/loss column (3) is below 2
(`ClearStatusIfENABLED`). Every buff scroll's status (rows 44-54) is 2, so the client used to hide
scroll buffs the server kept, and the server refuses the same scroll while it runs, so the icon
stayed gone for the hour. `DeleteWeaponBoundState` applies the same test; the two-handed-over-shield
clear is the server's one unconditional case (`ClearLWeaponSkillEffect(true)`). A status rebuilt
from spawn flags (`IsDurationUnknown`: skill entity, index 0) has no real duration, so UI2 icons
show "Remaining time unknown." instead of the 100 s placeholder; no timer counts back up past zero.
Real remaining times would need the server to send them with `tag_ADD_CHAR` (not done).
**A rebuilt status's row is a guess from its type alone** (`m_StateSTBIDXTable`: a Strength Scroll's
attack power reads as the skill buff, gain/loss 0), so the swap mirror skips it and the server's
word decides: `Change_EQUIP_ITEM` now sends `GSV_CLEAR_STATUS` with whatever the swap cleared
(before, it cleared silently and every client guessed; a party member who buffed out of view lost
the icon on a swap in everyone else's view).
**A potion's end reaches everyone nearby (2026-10-28, validated).** `Send_gsv_CLEAR_STATUS` sent a
potion-only clear to the party, while the potion's start goes to the sectors, so other players nearby
kept its heal-over-time icon (`CEnduranceItem` never ends by itself) for good. It goes to the sectors
now. `Recv_gsv_CLEAR_STATUS` reads no more HP/MP values than the packet carries and applies HP
through `Reconcile_HP`; `Recv_tag_ADJ_STATUS` skips both potion types (it compared a row to a type).

## Stun Feedback (2026-11-02)

`CStunFeedback` (`stunfeedback.*`), for the local player only. Players could not see they were

## Bone-Attached Particle Budgeting

Character model bone effects created by `CCharMODEL::CreateBoneEFFECT` are passive cosmetic effects and are registered with `CBoneEffectBudget` (`BoneEffectBudget.cpp/h`) using owner, NPC id, bone index, and effect hash. So are the ZSC dummy-point effects of equipped parts (`CObjCHAR::New_ModelDummyEFFECT`: imported backs, moving weapon pieces). Registration is intentionally narrow: do not add skill particles, hit effects, bullets, terrain/weather effects, item-table weapon effects, or general `g_pEffectLIST` effects to `BoneFx`.

The budget manager runs once per main-frame update after scene update. It prioritizes the player, the current target, visible + in-frustum owners, then nearest distance to the avatar. Off-screen owners are always Off. On-screen ones are Full until the summed configured particle capacity reaches **8,000**; past that ceiling the farthest degrade to Reduced, Minimal, then Off. That ceiling is for pathological scenes only -- a normal pack never reaches it.

The old crowd limits (480 particles, 360 emit/sec, 3 full copies per NPC/effect signature) predated batching and were removed on 2026-10-22 after an in-game A/B with `[VIDEO] BONE_FX_BUDGET=0` (lifts the ceiling; testing only, HUD shows `BoneFx (NO BUDGET)`). Measured on the mid-range target (RTX 5060, the hardware bar -- low-end is not targeted): 15 Thorns, 102 -> 1,020 live particles changed `scnupd` by 0 and `render` by ~0.2 ms; 30 Thorns at full tier (1,982 particles, 2 draws) ran at 184 FPS with `present` 0.3 ms, so GPU fill is not the constraint. Do not reintroduce crowd limits without a new measurement. The emit-rate figure on the HUD is informational only, and `GetAverageEmitRate`'s sustained cap divides by a PTL lifetime, and particles age at 4.8x real time (`zz_particle::update`, intentional), so it under-reports slot-limited emitters by up to 4.8x.

Particle tiers are stored on `CEffect` and applied particle-only:
- `Full`: normal emit/update.
- `Reduced`: emit scale 0.35, runtime cap 40% with a minimum of 8 particles per emitter.
- `Minimal`: emit scale 0.08, runtime cap 12% clamped to 2-6 particles per emitter, update every 150 ms.
- `Off`: stop emitter and clear live particles.

`CEffect::StartEffect()` must preserve the stored particle tier, especially `Off`, so relink/start paths do not restart disabled particles. Mesh and sound parts inside the same effect stay unchanged. Engine-side runtime caps live in `zz_particle_emitter` / `zz_particle_event_sequence`; when caps are lowered, particles above the cap are deleted so old full-tier particles do not keep updating.

The debug HUD line starts with `BoneFx:` and reports groups, effects, emitters, active particles, runtime cap, configured emit rate, tier counts, and top NPC id. Use it to validate cases like Frozen Thorn (`NPC 1528`) without relying on the generic `Fx` line.

## Particle File Cache (`CParticle::RegisterToNZIN`)

Every `CEffect` builds its emitters from the `.ptl` again, so a crowd spawning at once paid the file per emitter. 30 Frozen Thorns re-entering view (~50 spawns, 64 emitters) measured 6.4 ms in one frame: 1.9 ms `IsExistFile` (~30 µs a lookup) and 4.1 ms reading + parsing through the VFS. `IO_Effect.cpp` now keeps each `.ptl`'s bytes in a process-lifetime map (key: upper-cased path, `/` → `\`) and builds every emitter with `::loadParticleFromMem`; the same burst measured **0.5 ms**. An empty entry marks a missing file, which therefore logs once, not per spawn. `loadParticleFromMem` was given `loadParticle`'s `use_delayed_loading` rule so the two paths prepare device objects identically. The frame-spike log's `fx[...]` / `ptl[...]` groups time this (see `FrameProfiler::EffectStep`).

## Bone Particle Texture Batching

`CCharMODEL::CreateBoneEFFECT` and `CObjCHAR::New_ModelDummyEFFECT` also mark their `CEffect` particles with `SetParticleBatchRenderHint(true)`. These are the only client opt-in paths for particle batching; gameplay particles and normal world effects must not be hinted unless they are separately audited.

The engine batches only hinted particle emitters that are additive-safe (`D3DBLENDOP_ADD` with destination blend `D3DBLEND_ONE`) and whose sequences can share the same texture/render-state key. Mixed or incompatible emitters fall back to the original render path. This was validated with Frozen Thorn (`NPC 1528`) aura particles, which use additive `_shine_03.dds` sequences and previously paid roughly one draw call per particle.

Batching lives in `zz_particle_emitter::RenderParticleListWithBatching` and sequence vertex append helpers in `zz_particle_event_sequence`. It writes world-space particle vertices into shared dynamic buffers, then draws one or more chunks per texture/render-state group. The debug HUD line starts with `PartBatch:` and reports batch groups, particles, draw calls, fallback count, and estimated saved draw calls.

## Particle Emit-Accumulator (death-then-spawn timing)

`zz_particle_event_sequence::update` accumulates fractional emit budget in `m_fNumNewPartsExcess` and spawns when it crosses 1.0. The accumulator is **only consumed when a spawn actually succeeds** — i.e., inside the `while (m_fNumNewPartsExcess >= 1.0f && free_elements > 0 && ...)` loop, the `m_fNumNewPartsExcess -= 1.0f` happens immediately after a successful `CreateNewParticle`. This matches the Rust port's pattern at `rose-offline-client/src/systems/particle_sequence_system.rs:336-394`.

Do not restore the older pattern that decremented the accumulator unconditionally when it crossed 1.0 regardless of whether `free_elements` allowed the spawn. That bug produced a visible synchronised flash on every cosmetic emitter capped at `num_particles=1` (smoke-on-buildings in town hubs), because the emit accumulator's "ready to spawn" moment drifted out of phase with the death frame — sometimes the spawn fired the same frame the slot freed (no gap), but more often the next spawn-trigger was 1-5 frames away, leaving the slot empty for ~16-83 ms per cycle. SMOKE_04 on JZ01 chimneys was the canonical repro.

For finite emitters (`m_Loops > 0`), `remaining_for_loops` enforces the `m_Loops * m_iNumParticles` cap and the accumulator is clamped to that remaining budget so it cannot overshoot after the loop completes.

`m_fNumNewPartsExcess` is allowed to grow beyond 1.0 while the slot is full, and that is correct — it preserves the "spawn debt" so the replacement particle fires on the death frame instead of waiting for the accumulator to refill from zero. Don't add a cap unless you have a measured runaway case; for an infinite emitter at `emit_rate * life` the steady-state ceiling is bounded.

## Input Dispatch

Windows messages arrive in `CGame::AddWndMsgQ` (called from `WndProc`). For each message the active state's `ProcWndMsgInstant` runs **synchronously on the Win32 thread**; if it returns non-zero the message is consumed, otherwise it is queued in `m_WndMsgQ` and drained next frame by `CGame::ProcInput` → `ProcMouseInput` / `ProcKeyboardInput`.

The queued path for mouse messages calls `g_itMGR.MsgProc` → `CITStateNormal::Process`, which iterates **every open dialog** (`m_Dlgs`) and **every icon** (`m_Icons`) in reverse, calling `pDlg->Process(uiMsg, wParam, lParam)` on each for hit-testing. Cost is O(n_dialogs × n_controls) per drained message.

**Right-click camera drag**: `CGameStateMain::ProcWndMsgInstant` handles `WM_MOUSEMOVE` with `MK_RBUTTON` by calling `Add_YAW` / `Add_PITCH` (cheap, dirty-flag only) and **returning 1 to consume the message**. Windows delivers mousemove at 100–500 Hz during active drag; without the early return, each one would queue and pay the full dialog hit-test walk on the next frame, producing micro-stutters. No UI reacts to mousemove while RMB is held for camera control, so the consumption is safe. `m_ptCurrMouse` is updated in `AddWndMsgQ` **before** `ProcWndMsgInstant`, so global cursor tracking isn't affected.

Left-click, hover, and non-drag cursor motion otherwise flow through the queued path (UI must see them). Also consumed early: anything a UI2 panel handled (`RoseRmlUi::ProcessWndMsg`, first refusal in `CGameState::ProcWndMsgInstant`), whatever the `~` dev UI handles while it is on, and left clicks/drags on the overlay panels (item preview, Monster Inspector, damage meter, summon info).

## PVP: You Are Never Your Own Enemy

`CUserInputState::IsEnemy` (`jcommandstate.cpp`) is the client's single hostile/friendly verdict for players (attack click, cursor, `CheckCastingTargetFilter`). It switches on the target's `pvp_state`: in an `AllExceptParty` zone (Junon Cartel, Crusader Training Camp, Lion's Plains, Union War, Desert of the Dead) it answers "enemy" for anyone not in the party list, and in an `All` zone for everyone — including the avatar itself, which the party list never contains. The server's `CObjAVT::Is_ALLIED` already had the `pDestCHAR == this` case.

## Boss Attack Telegraphs (2026-10-18, validated in game: circle and cone)

A monster casting a skill flagged in `LIST_SKILL` col 83 (`SKILL_TELEGRAPH`; the column was
the dead "area hit effect") shows its area on the ground for the length of the cast: a
translucent red disc with a bright rim and a fill that grows to the rim as the cast runs,
then a flash when it fires. `CGroundTelegraphs` (`groundtelegraph.*`) starts one in
`CObjAI::ProcSkillCastingAction` (the client's real cast start; the length is one play of

`m_nActiveSkillIDX` no longer holds the skill (`Casting_END` covers fire, stop, stun,
death, cancel); fired = `m_nDoingSkillIDX` holds it in that frame; a hard limit covers the
one path that skips `Casting_END` (`SetCMD_MOVE`). Three shapes, as the server measures
them: a circle of `SKILL_SCOPE_RADIUS` around where the cast began (type 17, or any area
without an aim -- `Goto_TARGET` resets a monster's aim to itself), and for an aimed scope
(`SKILL_SCOPE_AIMED`: a frontal strip, or a cone, `SKILL_SCOPE_CONE` = 100000000 + length x
10000 + degrees) the strip or cone toward the server's aim. **The aim** is fixed by the game
server when the cast begins (`Casting_START`: the target's position into `m_PosGOTO`) and
rides on `GSV_SKILL_START` (`m_PosAIM`, present only when `m_nSize` says so). The client
keeps it in `CObjAI::m_PosSkillAIM` (pending until `ProcSkillCastingAction`, active until
`Casting_END`), and `FaceSkillTarget` turns the caster to it instead of to its moving target.
A start can reach a cast that is already playing (a remote cast held behind an owed swing
pops with its start flag still armed and begins before the packet): `Recv_gsv_SKILL_START`
then aims it on the spot and `CGroundTelegraphs::OnAimArrived` turns the fallback circle
into the cone, timing kept (Cerberus's first breath, 2026-10-18).
An aimed skill's area "bullet" effect (`CSkillManager::ActionSkill`, type 7) is also turned
to the caster's facing: it stands in the world at true size, where a casting effect would be
linked to the model and drawn at its scale (8x on Cerberus). The geometry samples `CTERRAIN::GetHeight` per vertex (lifted 20 cm: bilinear
heights against a triangulated mesh) and goes to the engine's ground overlay
(`::setGroundOverlay`, see `src/engine/CLAUDE.md`) every frame. **The player's aim, and any
shape centred on a deck** (more than 1.5 m over the terrain), take the surface nearest the
centre's height instead (`CGroundTelegraphs::Height`, 2026-10-29): the terrain or the top of a
walkable map object (`IsWalkableNode`: what `GetHeightTop` stands characters on), within 3 m
above and 5 m below, blended over a 1 m world lattice. Each lattice point costs a ray through
every object there, so they are cached (cleared per aim and per zone) and at most 40 are
sampled a frame; an unsampled point falls back to the terrain. The aim itself picks a deck
under the cursor first (`CSkillAim::MouseOnGround`). Users: the Warden's Seal
Burst (7023, a circle) and Cerberus's Hellfire Breath (7022, a cone), `import-cerberus.py`;
the Fearsome Terrasaurus King's Charge (3603, a 15 x 7 m strip down its lunge),
`terrasaurus-charge.py` (2026-10-24, the first retrofit: the wind-up re-cut so the cast
clip ends at the jump, since the server applies an area hit when the action clip starts).
**A missing telegraph is a missing cast:** read `remote cast abandoned` in client.log first
-- a stun-cancelled cast used to leave the remote-cast watchdog's stamp set and drop the
caster's next cast (fixed in `SetCMD_Skill2OBJ`).

## Summon Control (CTRL+Click)

CTRL+click lets a player command their summons (move / attack) instead of moving the avatar. The logic is in `CUserInputState::TrySummonControlClick` (`jcommandstate.cpp`), called at the top of **both** `ClickObject` and `DBClickObject` for the active `CSevenHeartUserInput` (and `CDefaultUserInput`):

- It is consumed (returns true, avatar does **not** move) only when the player owns a summon (`GetCur_SummonCNT() > 0`), is not riding, and CTRL is held (`wParam & MK_CONTROL`). Otherwise it returns false and legacy CTRL+click behavior (HP peek, drop-item info, item pickup, NPC/player clicks) is unchanged.

Sends go through `CSendPACKET::Send_cli_SUMMON_CONTROL_MOVE` / `_ATTACK` (`network/sendpacket.cpp`) using the shared `CLI_SUMMON_CONTROL` packet. The server is authoritative for which summons obey and how; see the gameserver `CLAUDE.md` "Summon Control" section (including the `IsMovablePOS` gotcha that made move orders look random).

## A Character Can Outlive Its Model Node

`CObjCHAR::m_hNodeMODEL` can be NULL on a live object that is still in
`CObjectMANAGER::m_CharLIST` and still `Proc()`'d every frame. `CObjMOB::Change_CHAR`
(`cobjchar.cpp`) was the clearest producer: it calls `DeleteCHAR()` — which nulls the handle
via `UnloadModelNODE()` — then `Create()`, and used to simply `return false` on failure. It
now rebuilds the previous character, and `Recv_gsv_CHANGE_NPC` deletes the object if even
that failed (`!HasModelNODE()`). `CObjAVT::Update` has the same unload-then-reload shape with
no failure handling.

**This is not benign, because `getPosition()` fails loudly and quietly at the same time.**
`zz_interface.cpp`'s `getPosition` logs `interface: getPosition() failed`, returns 0 — a
value every hot caller ignores — **and writes `ZZ_INFINITE` (1e9) into the caller's
out-parameter**. `CObjCHAR_Collision::AdjustHeight_Monster` then divides that into a patch
index and hands it to `CTERRAIN::GetPATCH`, which indexed a 64×64 array with no range test
at all until 2026-09-12. One broken object was an out-of-bounds read plus a likely garbage
pointer dereference, every frame, for the life of the process.

Rules:

- **Test the model node before any per-frame model access.** `CObjCHAR::HasModelNODE()`, or
  `HasModelNODEorReport(where)` which also names the object in the log exactly once. The
  guard lives in `CObjCHAR_Collision::UpdateHeight`, which covers all five `AdjustHeight_*`
  paths, and in `CObjCHAR::Proc`'s out-of-frustum branch.
- **The engine's two log lines have no subject and no rate limit.** `getPosition() failed` /
  `getVisibility() failed` name nothing and fire per frame per object — 32,107 and 6,838
  lines from **three** objects in one session, 77% of `error.txt`, which buries every other
  diagnostic. Never read a count of them as a count of broken objects; decode the per-frame
  pattern instead. Fix the caller, don't touch the engine log.
- **`getVisibility` is the stricter of the two** (it also runs an RTTI check) and returns
  0.0 = invisible, which silently makes the object unclickable in `CTERRAIN::Pick_OBJECT`
  and drops its nameplate in `CNameBox::Draw`. A nameless, unclickable monster is this bug's
  visible symptom.
- **Creation failures log at `LOG_WARN` now, not `LOG_DEBUG_`** (`Add_MobCHAR`'s "Mob
  character creation failed", `LoadModelNODE`'s "no skeleton for"). At debug level they were
  filtered out entirely, so the only evidence of a broken object was the subject-less engine
  line. `LogString` formats before it filters and always logs at Debug.

## Monsters Walk The Server's Floor (pathfinding Phase 6, 2026-10-29)

A monster, a summon or an NPC the server gave a floor (`gsv_MOB_CHAR` / `gsv_NPC_CHAR`
`m_nPosZ`, the `target_pos.z` of `CharacterMove` / `CharacterMoveAttack`, `gsv_STOP.m_nPosZ`;
-32768 = none) is drawn on that floor, not on `GetHeightTop`:
- `CObjCHAR::m_fNavRefZ` holds the floor.
- `CObjCHAR_Collision::MonsterFloorZ` follows it each frame with the server's step rule: the
  highest up-facing surface (`::getFloorBelowInScene`) no more than 135 cm above last frame's
  floor, never under the terrain.
- So one under a bridge stays under it. `GetHeightTop` would put it on the deck.
- `SetServerZ` re-seeds it on a spawn, and on a move or stop when none is held, when it is
  stale (1 s unfollowed) or more than 3 m off.
- No floor (a client-only puppet, `[nav] send_z = 0`): exactly the old behaviour. Avatars are
  untouched: they follow their own collision.
- **Other players** use `AdjustHeight_Other`, the avatar's foot test without the front spheres.
  Its contact filter (`CollisionCallback_Other`) keeps "not moveable" parts since 2026-10-31: it
  used to drop them, but only a map object's root part carries user data, so it dropped roots

  everyone else's screen while the ramp (children) looked fine. A player coming into view is
  placed on `gsv_AVT_CHAR.m_nPosZ`, the server's walked floor (-32768 = GetHeightTop as before).

- The move target's z stays the 0 it always was. The floor rides in the slot only to be read

## Dummy Indices: `getNumDummies()` Is Authored Count + 1, And A Valid Index Is `< count`

`zz_skeleton::load_skeleton` appends one extra root-bone dummy (`_p1`) to every
skeleton, so `::getNumDummies()` returns the `.ZMD`'s dummy count plus one and the
valid range is `0 .. count-1`. Four sites in the client tested `count >= index`, which
lets `index == count` through; the engine's `link_dummy` then hit a `zz_assertf` that is
**live in release** (the "Engine Assertion Failed" dialog), and its "Ignore" button
continued into `get_dummy()`, whose only guard is a compiled-out `assert()`, reading one
pointer past the dummy vector. Heap luck decided whether that faulted, and `_zz_assert`
remembers an ignored file:line for the session, so later hits went straight to the UB.

The trigger in the wild: `LIST_SKILL` links hit effects to the *target's* dummy 3
(Blood Attack 651-660, Twin/Triple Shot 2221-2240), and four monster skeletons ship
only two dummies -- `icanes_g` (Ikaness Soldier 1580, Ikaness Sweeper 2294), `s_kera01`
(Executor Kera 1719), `lep_bone` (Leprechaun 3003). Dump of 2026-09-17 01:11:46:
`zz_model::link_dummy` <- `CObjCHAR::LinkDummy` <- `ProcOneEffectedSkill`.

Rules now:

- **Go through `ResolveDummyIDX(hModel, idx, char_no)`** (`cobjchar.h`) for any
  data-driven dummy index. It clamps an out-of-range request to the *last* dummy -- the
  engine's `_p1` root dummy, the same attach point `Link2LastDummy()` uses for bullet
  impacts -- and logs once per (char_no, index) at `LOG_WARN`. Rejecting used to be
  worse than clamping: both hit-effect call sites ignore `LinkDummy`'s return value and
  `InsertToScene()` the unlinked effect anyway, so on Lizards, Tumblers, Bonfires and
  every zero-dummy skeleton the blood splash played at the world origin.
- The engine's `link_dummy` / `get_dummy_position_world` now refuse a bad index with a
  `ZZ_LOG` line (`model: link_dummy(...) refused`) instead of asserting, and the
  `linkDummy` export returns 0. That is the backstop for the raw `::linkDummy` callers
  (ZSC-driven `io_model.cpp`, trails, cart parts); it is an engine change, so the exe
  and `znzin.dll` deploy as a pair.
- **`INVALID_DUMMY_POINT_NUM` (999) means "link to the model root", and every site must
  test for it before calling `LinkDummy`.** The self-skill branch of
  `CSkillManager::...` in `gamecommon/skill.cpp` (types 8/10/12/17 -- Holy Blood 540 was
  the tell) passed the column straight through; with the old guard that failed silently
  and left the effect unlinked at the world origin, with the clamp it logged a spurious
  `Dummy index 999 requested on char_no 0` warning. It now does `LinkNODE(GetZMODEL())`
  like the hit-effect and casting-effect sites. Over a thousand LIST_SKILL rows use 999 for the
  hit effect, so a 999 in the warning is always a missing sentinel check, never data.

Validated in game 2026-09-17: 9 Blood Attacks on an Ikaness Sweeper (2294), one
`Dummy index 3 requested on char_no 2294` warning, no dialog, splash on the body.

## Frame Timing & Timer Precision

`g_GameDATA.GetElapsedFrameTime()` ([game.cpp:172,180](game.cpp#L172)) is built on `timeGetTime()`. By default Windows quantizes `timeGetTime()` to the system tick (~15.6 ms), which dominates anything driven by per-frame dt above 60 fps:
- 50 Hz (20 ms real frame): measured dt = 15.6 or 31.2 → ±25% variance around mean.
- 75 Hz (13.3 ms real frame): measured dt = 0 or 15.6 → ±100%+ variance, even when frames are perfectly smooth.

`WinMain` instantiates `HighResTimerScope` ([winmain.cpp](winmain.cpp#L26): the class at line 26, the instance on the first line of `WinMain`) which calls `timeBeginPeriod(1)` for the lifetime of the process and `timeEndPeriod(1)` on exit. Do not add a second `timeBeginPeriod(1)` somewhere else; the WinMain RAII covers everything. Do not remove it — the symptoms it cures (jittery RMB camera, jerky dialog-drag, "stutter that only goes away at 50 Hz") look like a frame-pacing or driver bug but are pure timer-quantization downstream of `GetElapsedFrameTime()`.

**Diagnostic**: if a stutter seems to span unrelated subsystems (camera + UI + animation) and gets worse as monitor refresh rate climbs above the 64 Hz timer rate, suspect timer precision before swap-chain queue depth or driver state. Confirm with `QueryPerformanceCounter` traces of actual frame durations alongside `timeGetTime()` deltas — they should agree.

## Device, Swap Chain & Screen Modes

The client runs on a **Direct3D 9Ex** device when the platform provides one, falling back to plain D3D9 otherwise. Full design notes, rationale and the outstanding gaps live in [doc/d3d9ex-migration.md](../../doc/d3d9ex-migration.md) — read that before touching device creation, present, or reset. Highlights that bite from the client side:

- `D3DPOOL_MANAGED` is **illegal** on a 9Ex device and is gone from everything we compile. New device resources go in `D3DPOOL_DEFAULT` and must survive the invalidate/restore cycle. `D3DPOOL_SYSTEMMEM` is still legal and is the escape hatch for anything that genuinely needs `LockRect`.
- **`d3dx9_43.dll` is a hard runtime dependency.** D3DX9 is no longer statically linked; the client will not start without the DLL next to it. The old 2005-era static D3DX allocated `ID3DXFont`'s glyph cache in `D3DPOOL_MANAGED`, so on a 9Ex device font creation succeeded but `DrawText` silently drew nothing — no chat, no item names, no player names, while sprites (and therefore the rest of the UI) rendered fine. If text vanishes wholesale, suspect the D3DX runtime before the font code.
- **A/B switch:** `rose-next.ini` → `[VIDEO] D3D9EX=0`, or `ROSE_NO_D3D9EX=1` in the environment, forces the legacy path. Always confirm via the log which path is live — a toggle that silently does nothing produces a false negative (this cost a debugging round).
- **Occlusion skips the frame.** When the window is minimised (or another app owns the monitor fullscreen), `throttle_if_occluded()` makes `::beginScene()` return false, so the render is skipped rather than drawn and discarded — the same contract a lost device already used, which is why no state code changed. Note `background_render` is unaffected: a visible-but-unfocused window is *not* occluded. **If you touch this:** skipping the frame stops `swap_buffers()` running, and that is the only thing that *sets* the occluded flag, so the poll of `CheckDeviceState()` inside `throttle_if_occluded()` is what un-latches it. Drop the poll and the client goes black on the first minimise and never comes back. Skipping waits for 2 consecutive occluded presents — the compositor reports one-frame blips during normal play and dropping a frame for those is a visible hitch buying nothing.
- **An occlusion log line is not a black screen.** A skipped present leaves the previous front buffer on screen, so the throttle costs a dropped frame, never a blank one. If occlusion lines correlate with something visibly black, the display itself is being handed back and forth — look at mode ownership, not at the render loop. Read the `iconic=`/`foreground=`/`elapsed=` fields before theorising: a genuine minimise and a compositor blip produced identical logs before those existed, and the first "reproduction" chased under the new logging turned out to be a real 23-second minimise. Write-up in [doc/d3d9ex-migration.md](../../doc/d3d9ex-migration.md).

Present parameters (`zz_renderer_d3d::initialize`, the `_parameters` block -- [zz_renderer_d3d.cpp:878-920](../engine/src/zz_renderer_d3d.cpp#L878-L920)) intentionally use:
- `BackBufferCount = 1` — minimum flip-queue depth, makes it harder for a missed-vsync frame to lock the pipeline into a half-rate beat.
- `SwapEffect = D3DSWAPEFFECT_DISCARD` (regardless of FSAA) — runtime-managed back buffers instead of `D3DSWAPEFFECT_FLIP`'s driver-managed flip queue, which on AMD could pin the present cadence after a single overrun. **`D3DSWAPEFFECT_FLIPEX` was evaluated and rejected** — it conflicts with MSAA (a live user setting) and with the `Present(..., hwnd, ...)` destination-window override; see the migration doc for why the motivating symptom turned out to be something else entirely.

These were tightened while diagnosing the sticky-stutter bug. Neither change alone fixed the perceived stutter — the timer-precision fix above did — but both narrow the surface for residual driver-side queue pathologies and are kept defensively. Do not raise `BackBufferCount` back to 2 or restore `D3DSWAPEFFECT_FLIP` without a measured reason.

**Vsync is the default frame cap.** `zz_system::sleep()` also paces to `max_framerate`, but INIT.LUA's `setFramerateRange(15, 1000)` leaves that uncapped unless `[VIDEO] MAX_FPS` is set (honoured only with `VSYNC=0`; see src/engine/CLAUDE.md). The presentation interval is decided **once, after** the fullscreen/windowed split (the `state.use_vsync` block, [zz_renderer_d3d.cpp:932-942](../engine/src/zz_renderer_d3d.cpp#L932-L942)); keep it that way. The windowed branch used to hardcode `D3DPRESENT_INTERVAL_IMMEDIATE` and ignore `state.use_vsync` (which defaults to true), so windowed mode ran unbounded while fullscreen was capped — which also accounted for the long-standing "windowed feels worse than fullscreen" impression. `[VIDEO] VSYNC=0` in `rose-next.ini` uncaps deliberately. INIT.LUA:46 calls the exported `useVSync(1)`, but the renderer reads `[VIDEO] VSYNC` after it at every device creation (with the script's value only as the default), so the INI is the knob that counts.

### Three screen modes, and which predicate to use

`e_ScreenMode` (`capplication.h`) is `SCREEN_MODE_WINDOWED` / `_BORDERLESS` / `_EXCLUSIVE`. **Borderless is the default fullscreen** — `[VIDEO] EXCLUSIVE_FULLSCREEN=1` in `rose-next.ini` (or `ROSE_EXCLUSIVE_FULLSCREEN=1`) opts back into the legacy exclusive device, which is also the A/B switch for the black-flash bug it was introduced to fix. `[VIDEO] FULLSCREEN` keeps its old 0/1 meaning and is still what the options dialog persists; `PreferredFullscreenMode()` decides which flavour a "1" means, and `SetFullscreenMode(bool)` survives as a shim over `SetScreenMode()` so the existing call sites (WinMain, Alt+Enter, the options radio) are unchanged.

Picking the wrong predicate is the easy mistake here, because borderless is *fullscreen to the player* and *windowed to D3D*:

| Predicate | True for | Use it for |
|---|---|---|
| `IsFullScreenMode()` | exclusive only | anything feeding `setScreen(..., use_fullscreen)` → `D3DPRESENT_PARAMETERS::Windowed` |
| `IsWindowedFrame()` | windowed only | "can the user drag this frame / does it have a caption" — `WM_SIZE` handling, the FPS title text, the options radio, Alt+Enter |
| `IsBorderless()` | borderless only | the monitor-sized special cases |

`ChangeScreenMode()` and the options dialog must test `IsWindowedFrame()`, not `!IsFullScreenMode()` — the latter is true in borderless, so Alt+Enter would ask for a mode it is already in and rebuild the device for nothing.

**A borderless backbuffer is always the monitor size.** `ResizeWindowByClientSize` overwrites the requested resolution with `GetMonitorRect()` in that branch, so the resolution list is a deliberate no-op there. A `WS_POPUP` window gets exactly the client area it asks for, so a mismatched backbuffer would be stretched by D3D and drift every hit-test — the failure the next section exists to prevent. Borderless is also **not** `WS_EX_TOPMOST`: the exclusive path uses it because an exclusive device owns the display anyway, but on a plain window it only makes the game fight for the top of the z-order.

`ApplyWindowedClientResize` early-outs unless `IsWindowedFrame()`. Borderless has nothing to react to (`WM_SIZE` there would mean a monitor reflow, and each one costs a full device teardown).

### Window sizing must match the backbuffer

In windowed mode the backbuffer is created at the requested client size and D3D **stretches it to whatever the client area actually is**. Mouse input is raw client pixels, so any mismatch silently desyncs hit-testing from what is drawn — the error grows with distance from the origin, which reads as "the checkbox is a bit off" rather than an obvious break.

`CApplication::ResizeWindowByClientSize` therefore clamps against the room actually left for the *client* area (`SM_C*MAXTRACK` minus the decoration size), not against the raw screen size, and re-syncs the renderer if the granted client rect still differs from the request. Windows refuses to size a `WS_THICKFRAME` window past `SM_C*MAXTRACK` unless the app handles `WM_GETMINMAXINFO`, which this client does not — so on a 1920×1080 desktop a requested 1080-tall client area came back as 1061 and everything below the top of the screen drifted.

Frame drags are handled by `CApplication::ApplyWindowedClientResize`, driven from `WM_ENTERSIZEMOVE` / `WM_EXITSIZEMOVE` / `WM_SIZE`. It **accepts** the client area Windows gave us and rebuilds the device to match — deliberately *not* calling `ResizeWindowByClientSize`, which would `MoveWindow` the window the user is dragging. Three guards matter, and each closes a real failure rather than a theoretical one:

- **Deferral.** `WM_SIZE` fires continuously during a drag and every resize is a full device teardown, so the work waits for `WM_EXITSIZEMOVE`. Maximise/restore/programmatic sizes arrive outside a drag and apply immediately; `SIZE_MINIMIZED` is skipped (zero client area, and a reset with a zero-sized backbuffer fails).
- **Re-entrancy** (`m_bResizingEngine`). Our own `MoveWindow` posts `WM_SIZE` synchronously, so the handler would otherwise recurse into the resize. `ResizeWindowByClientSize` and `SetScreenMode` both hold this for their duration — the latter because `SWP_FRAMECHANGED` posts `WM_SIZE` while `m_ScreenMode` still holds the *old* value, which would rebuild the device for a size `ChangeScreenMode` is about to replace.
- **Engine lifetime** (`m_bEngineReady`, set after `Init_DEVICE`, cleared before teardown). The window is created *before* `initZnzin()`, so `znzin`/`state` are null in between. Note `CHECK_INTERFACE` in `zz_interface.cpp` is only a **profiler hook** — it does not null-check anything, so `setScreen()` would happily dereference null.

### Diagnostic logging

`client.log` verbosity is a runtime switch resolved in `winmain.cpp::ResolveLogLevel()`:

```
rose-next.ini  ->  [LOG]  LEVEL=debug
environment    ->  ROSE_LOG_LEVEL=debug     (wins over the ini)
```

Accepted: `trace` / `debug` / `info` (default) / `warn` / `error` / `off`; anything else
falls back to `info`. The resolved level is echoed into the log itself as
`Log level: <name>`, so a handed-over log states its own verbosity — without it a log with
no `CombatTrace` lines reads identically whether the trace was off or the traced code never ran.

**Everything diagnostic reports at Debug.** `LogString(LOG_DEBUG_, ...)` maps to
`LogLevel::Debug`, which covers all `CombatTrace` lines (queued/popped/discarded damage
events, server swings, skill classification), skill tracing and the streaming counters. It
is also *loud*: terrain streaming logs per object, so the file grows fast and the
`fmt::sprintf` cost lands on exactly the frames that already hitch (see `rose/common/log.h`).
Keep repros short and put it back to `info` afterwards.

**Trimmed 2026-09-29.** Asset-loading chatter (`loadVisible`/`unloadVisible`, `Object:: Map`,
`CObjTREE`, lightmap `SET LIGHT MAP`, `Load FILE`/`Free FILE`, `HashMotionFILE`, `SKEL::`) and the
per-call Lua echo (`lua function( ... ) return`, ~50 lines a second from `CheckTutorialEvent`)
now log at **Trace** (`LogStringTrace`, printf-style like `LogString`) -- set `LEVEL=trace` to
get them back. `legacy_printf` strips the message's trailing newline, which the logger's own

  cur_speed frame_ms` -- a move of 3 m or more between two frames, whatever caused it (packet,
  snap, engine node read-back, collision), from the top of `CObjCHAR::Proc`.
- The local avatar is traced too (same Debug switch): `CombatTrace avatar command: ...` for its own
  command changes (the remote line's fields plus `dist_target`) and its queue drops;
  `avatar swing sync: event self_drift client_dist server_dist range` per confirmed swing
  (`PosGOTO` of a `CombatSwing` is the server's own position for the attacker, so `self_drift` is
  client-vs-server avatar position); `avatar attack walks (between swings | closing in): dist range`
  when the attack loop walks instead of swinging. They ruled out range and position as the cause of
  the avatar's hit lag (it was the cast cycle, see the own-hit fold above).
- `CombatTrace queued command dropped, never validated / superseded by <type> / cleared by
  skill start: obj N type <type>` -- `CObjCommandManager` silently deletes orders: only skill
  commands are ever validated, so a queued move/attack/stop is discarded at the pop, and a push
  discards everything queued that is not a skill command with its result (a monster's held cast
  included).
- `CombatTrace GSV_STOP received: obj N` -- the server as the cause of a stop.
- `CombatTrace move received: obj N move|move_attack target T speed S (was W) server_dist
  client_dist command state` -- each `CharacterMove` / `CharacterMoveAttack` for a traced
  monster (2026-10-15). A monster's speed reaches the client only this way, so a slow shows as
  `speed 260 (was 500)` when it lands and the reverse when it ends; `server_dist` against
  `client_dist` is the two copies' gap at that moment. `CombatTrace status cleared: obj N
  cleared 0xF` marks a status ending (`0x80` = slow). The server side is `CombatTrace server
  move speed resync` (see the gameserver CLAUDE.md, "A Monster's Move Speed Must Reach The
  Client").
- `CombatTrace position snapped forward: obj N jump J client_dist C server_dist S` --
  `Adj_MoveSPEED` jumps a non-avatar that is more than a second of walking behind the server's
  copy (its computed catch-up speed is never applied); this is the visible "teleport".

The file is `client-YYYY-MM-DD.log` in the game directory, opened in **append** mode — it
accumulates across runs on the same day, so delete it (or note the wall-clock time of the
repro) before capturing. It flushes per record, so it survives a hard crash; `error.txt`
does not.
