## NPC Overhead Quest Icons

WoW-style "!" / "?" markers above NPC heads. The retail scaffolding (`CObjNPC::m_nQuestSignal`, the `QUEST_EMOTICON_*` draw in `CNameBox::DrawNpcName`, `CObjUSER::m_bQuestUpdate` set on `Recv_gsv_QUEST_REPLY` and reset after the char loop in `CObjectMANAGER::ProcOBJECT`) existed but was dead — only the later Evolution-era client filled the signal, via a Lua data table (`SC_QF_GetNpcQuestStatus`) our data never had, and none of that mechanism applies here (the `Project 137` folder is an experimental Evo build — archaeology only, not a design reference). Our evaluator is **client-only** and derives everything from the NPC's own conversation:

- **Evaluation** (`CEvent::GetQuestSignal`, `event/cevent.cpp`) has two mechanisms, both anchored on the NPC's own conversation. Signal: **3** = turn in, **1** = available, **0** = nothing (signal 2 = in-progress emoticon exists in the draw switch but is never set). Turn-in always beats available.
  - **Retail/QSD path (covers ALL quests, including retail):** `ScanQuestTriggerRefs()` harvests printable string constants from the `.CON` Lua blob — trigger names are readable even in compiled Lua 4 bytecode because binary length/type bytes separate constants — and keeps the ones that resolve in `g_QuestList`. Each trigger's `check_next` chain is walked the way `CheckQUEST` walks it (`ResolveQuestTrigger`: `CQuestTRIGGER::Proc(..., false)`, conditions only, no side effects; `COND_013` always passes client-side), and only the first link that passes is classified by reward composition (`ClassifyOneTrigger`, via the `CQuestTRIGGER::GetCOND/GetREWD` accessors, `io_quest.h`) — a chain can hold both an advance and an offer (`4411-02`/`-03`, Captain Bruise), and judging the whole chain showed "?" over an offer. The chain-wide union (`ClassifyQuestChain`) only decides whether a harvested name is kept. Reward rules: `REWD_000` op 1 (add quest) → **accept**; `COND_000` (has quest) + op 2 swap / op 3 reset-start, or op 0 delete *with* a grant (`REWD_001` give, 3/5/6/14) → **turn-in**. Delete-only chains are quest-*abandon* options and stay unclassified (op 4 is select-context only, ignored). Accept refs are additionally guarded with `Quest_GetRegistered` so an already-taken quest never re-shows `!`. Coverage measured over retail data: 737 dialog-referenced triggers → 152 accepts, 281 turn-ins, 7 abandon-only filtered.
  - **Quest-editor Lua path (dialog-exact fallback):** node-tree check funcs — bare `CHK_accept`/`CHK_complete` (replace-mode givers) and `QE<sn>_CHK_*` (QEX1 append) — run in a **throwaway** `classLUA` state (same load order as `Start()`: main blob → appendix → `QF_Init`), so an open dialog's `m_pLUA` is never disturbed. Function existence is checked via `GetGlobal` first (no "function not found" ErrorBOX). Editor quests are also covered by the QSD path (their trigger names appear in the generated Lua source), so this path only decides anything when custom check logic diverges from raw trigger conditions.
- **A passing trigger is only a candidate — the dialog has the last word (2026-09-20).** The `.CON` decides what to show from its *own* Lua, which gates on things the QSD never sees, so the QSD path alone lit "!" over NPCs with nothing to accept. Three live cases in Zant on one level-70 character: **Spero** — his whole quest line (2000-2011) sits behind `TA_hideMenu`, a check that returns 0 unconditionally (retail switched the chain off in the dialog and left `2000-01` passing in `QL-104.QSD`); **Cornell** — quest 5009 is a *daily timed* quest gated on `QF_getNpcQuestZeroVal(owner) == 1`, and `COND_011` (NPC variable) always returns true client-side; **Judy** — festival quests gated on an event value nothing sets (she has no AI). `CEvent::CollectReachableTriggers` therefore walks the conversation headlessly, exactly as `Conversation()`/`Click_ITEM` would (`ProbeMenu`: within one menu a passing NPCSAY/NEXTMSG clears the options gathered so far, so the last passing NPC line wins; every surviving option is "clicked" and its child opened as a new screen), and a candidate only counts if a **visible** node function names it via `QF_doQuestTrigger` / `QF_checkQuestCondition`. Names from a *failing* check are dropped again (it may name the trigger before the clause that rejects it). Applies to turn-ins too. It runs only when the QSD path produced a candidate, so an NPC with nothing on offer costs no Lua state.
  - **The probe state must be inert**, because the walk runs click functions. `QF_InitProbe` (`lua_init.cpp`) calls `QF_Init`, then re-includes the two generated `*_reg.inc` lists with `ZL_REGISTER` redefined so every binding that is not on the pure-getter whitelist becomes a no-op returning 0; `QF_doQuestTrigger` records and returns 1, `QF_checkQuestCondition` records and runs the real condition walk. **A new side-effecting `GF_`/`QF_` binding is inert by default; a new *getter* a dialog gates on must be added to `s_szProbeSafeFuncs`**, or that gate reads 0 in the probe and the icon disagrees with the dialog.
  - **The walk runs quiet and mirrors the screen (2026-11-05).** It repeats every 2 s, so one Lua error in it re-opened the "Script running error.." `MessageBox` forever: the Ferrell Guild manager (EM02-009) became a candidate once the tester joined the guild, and the walk "clicked" `AT_mileageBank`, which calls the retail `GF_openDeliveryStore` our client never registered (35 `.CON`s call it; 7 other unregistered `GF_` names exist, e.g. `GF_SwapItem`, `GF_IsWorldName`). Two fixes: `ProbeMenu` skips options with no text in the client's language (`Conversation` drops them at `ParseMESSAGE`, so nobody can click them -- 147 such options carry a click function), and `CEventLIST::GetNpcQuestSignal` wraps the evaluation in `lua_SetQuietErrors` (`lua_func.h`): no box, the first failure is logged once per file as a `Quest icon: script error in ...` warning with the Lua text (`lua_CaptureErrorText` hooks `_ERRORMESSAGE` in both throwaway states). A failing check still reads as "not passing", exactly as before.
  - `GetQuestSignal` now takes the asking NPC's client index: `QF_getEventOwner` reads `m_iOwnerObjIDX`, and a `CEvent` is cached per *file*, so the probe sets it for the walk and restores it (an open dialog on another NPC sharing the `.CON` keeps its own).
  - Fail-open: if the probe cannot run (no Lua, load error) the unfiltered QSD verdict stands. Known blind spot: 435 of 437 classified triggers are named by some node function; the two that are not (`PvP1301-110`/`-210`, EM02-008/-010) can no longer show "!".
  - **Timed quests do work, in a narrow window.** Cornell's `NPC_1001.aip` idle pattern opens 5009 when the *server's local clock* is 19:50-19:51 (event value 0 -> 1, with a shout), closes it at 23:57-23:59 (-> 3), and the trigger is an edge: a server started after 19:51 skips that day. Test with GM `/npc 1001 VAR 0 1` — the value reaches the client by `GSV_SET_EVENT_STATUS` and the "!" follows within the 2 s refresh.
- **Refresh** (`CObjNPC::Proc`, `cobjchar.cpp`): re-evaluates when the signal is unset (spawn), when `g_pAVATAR->m_bQuestUpdate` is set (quest add/del/trigger packets), and every `QUEST_SIGNAL_REFRESH_MS` (2 s) to catch conditions without a packet of their own (fetch-item counts, level checks). `CEventLIST::GetNpcQuestSignal(Get_INDEX(), m_nQuestIDX)` resolves `EVENT_FILENAME` and uses the normal cached `CEvent` list, so the `.CON` is parsed once.
- **Draw** (`CNameBox::DrawNpcName`): 32×32 sprite centered above the name (gated by the existing `IsShowNpcName` option, like the name itself). Skips drawing when `GetImageNID` returns −1 (sprites not installed).
- **Sprites**: `QUEST_EMOTICON_POSSIBLE`/`_ING`/`_COMPLETE` in module 0 (`Ui.TSI` + `UI_strID.ID`), texture `3DDATA/CONTROL/RES/QUESTEMOTICON.DDS` (128×32 uncompressed BGRA, three 32×32 cells). Installed by `scripts/add-quest-emoticons.py` (idempotent; placeholder "!"/"?" glyphs, or `--icons a.png b.png c.png` for real art; swapping just the DDS also works since the TSI rects stay valid). Gotcha: retail `Ui.TSI`'s total-sprite field lies (690 vs 688 actual); the client fills sprites from per-texture counts, so real indices start at 688 — the script handles this.
- **Deploy gotcha (cost a debugging round):** `UI_strID.ID` is loaded via plain `fopen` (`CImageIDMgr::LoadResourceFile`) from the **loose** `3ddata\control\xml\` folder in the launch dir — the VFS never covers it. Ship the updated `.ID` file loose alongside the rebaked VFS, or `GetImageNID` returns −1 and the icons silently don't draw (the draw guard hides missing sprites by design). `Ui.TSI`/`QUESTEMOTICON.DDS` load through the VFS normally.
- **Status:** validated in-game 2026-07-16 (Ronk / quest 5512: "!" when available, "?" when the fetch items are collected). Placeholder art is considered good enough for now; real icons can be swapped in later via the script's `--icons`.
